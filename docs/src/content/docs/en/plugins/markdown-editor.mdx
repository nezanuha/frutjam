Most markdown editors hide your `<textarea>` and edit a copy of it. This one
styles the textarea you already have and leaves it as the field you type into.

That one decision is why there is nothing to wire up. `required` still blocks a
submit. `FormData` still has the markdown in it. htmx, Turbo, your
unsaved-changes guard and your server all keep working, because as far as they
are concerned nothing changed.

## Installation

Two files: the script and the stylesheet. The stylesheet is separate from 2.0,
so link it or import it — if you forget, the editor still works and tells you
what is missing in the console.

<Snippet view="code">

```bash
npm install markdown-text-editor
```

</Snippet>

<Snippet view="code">

```javascript
import 'markdown-text-editor/style.css';
import MarkdownEditor from 'markdown-text-editor';

new MarkdownEditor('#notes');
```

</Snippet>

No build step? Use the CDN. The `<script src>` build carries marked and
DOMPurify inside it, so this is everything:

<Snippet view="code">

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/markdown-text-editor@2/dist/markdown-text-editor.css">
<textarea id="notes" name="content"></textarea>

<script src="https://cdn.jsdelivr.net/npm/markdown-text-editor@2/dist/markdown-text-editor.min.js"></script>
<script>new MarkdownEditor('#notes');</script>
```

</Snippet>

Or as an ES module, straight from the CDN with no bundler:

<Snippet view="code">

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/markdown-text-editor@2/dist/markdown-text-editor.css">
<textarea id="notes" name="content"></textarea>

<script type="module">
  import MarkdownEditor from 'https://cdn.jsdelivr.net/npm/markdown-text-editor@2/dist/markdown-text-editor.es.js';
  new MarkdownEditor('#notes');
</script>
```

</Snippet>

TypeScript types ship with the package. Nothing to install, and the options,
toolbar entries and variable shapes are all checked.

## Two ways to write

This is the thing people miss, so it is the second thing on the page: there are
**two modes**, and the one you get by default is not the interesting one.

### Hybrid — formatting appears as you type

`mode: 'hybrid'`. Headings get bigger, bold goes bold, links underline, and the
markers stay visible and editable. Nothing is hidden from you, and the text in
the box is still markdown.

```javascript

```

### Plain — the markdown, as written

The default. Monospaced, no styling of the source, and the preview button shows
you the rendered version when you want it. Pick this where people know markdown
and want nothing in the way.

## Every option, in one table

All of them are optional. Leave one out and you get the default.

Options are read **once**, when the editor is created. Changing them afterwards
does nothing: call `destroy()` and make a new editor.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Option | Type | Default | What it does |
| --- | --- | --- | --- |
| [`mode`](#two-ways-to-write) | `string` | `'plain'` | `'hybrid'` shows formatting as you type. |
| `placeholder` | `string` | — | Shown when empty. A `placeholder` already on the textarea wins. |
| [`toolbar`](#toolbar) | `array` | the 19 tools that need no setup | Which tools, in which order. Replaces the default rather than adding to it. |
| [`footer`](#status-bar) | `boolean \| object` | on, without `words` | The status bar. `false` hides it, an object picks the counts. |
| [`find`](#find-and-replace) | `boolean` | `true` | `Ctrl+F`. `false` gives the shortcut back to the browser. |
| [`tableBar`](#editing-tables) | `boolean` | follows the toolbar | The bar beside a table. `true` offers it without the table tool, `false` never. |
| [`pasteHtml`](#pasting-formatted-text) | `boolean` | `true` | Pasted rich text becomes markdown. `false` always pastes plain. |
| [`autosave`](#draft-recovery) | `boolean \| object` | `false` | Keeps a draft in the browser. Object form: `key`, `maxAge`, `debounce`. |
| [`variables`](#variables) | `array \| object` | — | Your placeholders. Object form: `` `{ items, complete }` ``. |
| [`upload`](#uploading-files) | `string \| object \| function` | — | Where files go. A URL, a config object, or your own function. |
| [`theme`](#theming) | `string` | inherited | `light`, `dark`, `snowberry`, `darkberry`. |
| `minHeight` | `number` | `200` | Pixels it shrinks to. |
| `maxHeight` | `number` | `500` | Pixels it grows to before scrolling. Draggable past it. |
| [`renderer`](#custom-renderer) | `function` | `marked` | Markdown in, HTML out. |
| [`sanitizer`](#custom-renderer) | `function` | `DOMPurify` | HTML in, safe HTML out. |
| [`onChange`](#reacting-to-changes) | `function` | — | Called with the markdown on every change. |
| [`locale`](#interface-language) | `object` | — | Translations for the editor's own words. |

</DocTable>

Every feature that is not a toolbar button has one option named after it. Pass
`false` to turn it off, or an object where there is something to configure.

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', {
    mode: 'hybrid',
    toolbar: ['bold', 'italic', 'table', 'preview'],
    footer: { words: true },
    find: true,
    tableBar: true,
});
```

</Snippet>


## Set it up for the job

Four shapes that cover most fields. Each one is a live editor — type in it, then
copy the config.

### A comment box

No headings, no images, nothing that turns a comment into an article. Counts
characters and words, since a comment usually has a limit.

<RawHtml html={"<div class=\"not-prose my-5\" style=\"min-height:15rem\"><p class=\"mte-demo-label\">Live demo &mdash; type in it</p><textarea class=\"mte-comment\" rows=\"4\" aria-label=\"Markdown editor demo, set up as a comment box\" placeholder=\"Leave a comment...\"></textarea></div>"} />

<Snippet view="code">

```javascript
new MarkdownEditor('#comment', {
    toolbar: ['bold', 'italic', 'strikethrough', 'link', 'code', 'ul', 'ol'],
    footer: { chars: true, words: true, line: false, col: false },
    minHeight: 140,
    find: false,            // Ctrl+F stays the browser's
});
```

</Snippet>

### A CMS body field

Hybrid, because the person writing the post is not thinking about asterisks.
The heading dropdown starts at H2, since H1 belongs to the page template.

```javascript
new MarkdownEditor('#body', {
```

</Snippet>

### A template or email editor

The one people reach for merge tags in. The dropdown inserts them, typing
`{{` completes them, and the preview shows the sample values so the layout
reads like a real message.

## Toolbar

Leave `toolbar` out and you get every tool that works with no setup, in this
order:

<Snippet view="code">

```javascript
// the default, written out
toolbar: [
    'undo', 'redo',
    'heading', 'blockquote',
    'ul', 'ol', 'checklist', 'outdent', 'indent',
    'bold', 'italic', 'strikethrough', 'code',
    'codeblock', 'hr', 'table',
    'link', 'image',
    'preview',
]
```

</Snippet>

Two tools are missing from it, and both for the same reason — neither can work
until you supply something:

- **`math`** needs a [`renderer`](#maths) that understands TeX. Without one the
  button would insert `$x^2$` and the preview would show the dollar signs.
- **`variables`** needs [your own list](#variables) of placeholders. With
  nothing configured it draws no button at all.

That is the rule for anything added later too: **on by default if it needs no
configuration, opt-in if it does.**

Passing `toolbar` **replaces** the default rather than adding to it. A list you
write out stays exactly as written and will not grow new buttons in a later
version — which is the point, for a toolbar curated down to five. If you want
the defaults, leave the option out instead of copying the list above.

### Pairs that close themselves

Six pairs close as you open them, which earns its keep most on links, where
`[text](url)` is four of them in a row:

<Snippet view="code">

```text
{ }    [ ]    ( )    < >    " "    ' '
```

</Snippet>

Type an opening one and you get both halves with the caret between them. Type
the closing half yourself and the caret steps over the one already there
instead of leaving you a spare. Select a word first and the pair wraps it —
select `text`, press `[`, and you have `[text]` with the word still selected,
ready for the `(url)` half. Backspace between an empty pair takes out both.

There is no option for this; it is always on.

### Heading levels

H1 usually belongs to the page, not the content. Narrow the dropdown and the
keyboard follows:

<Snippet view="code">

```javascript
new MarkdownEditor('#body', {
    toolbar: [{ heading: { levels: [2, 3, 4] } }, 'bold', 'italic', 'preview'],
});
```

</Snippet>

`Ctrl+1` to `Ctrl+3` map onto the list you gave, so a level you left out cannot
be typed from the keyboard either, and the tooltip only claims the shortcuts
that work. The order you write them in does not matter — the menu is always H1
first. Junk is ignored with a console warning and you get all six back rather
than an empty menu.

This restricts the toolbar, not the document: someone can still type `# Title`
and it renders as a heading, because what counts as markdown is the renderer's
business. If the rule has to hold, hold it on the server.

## Custom tools

A button of your own, dropped into the array wherever you want it. No forking,
no build step.

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', {
    toolbar: ['bold', 'italic', {
        custom: {
            title: 'Callout',
            icon: '<svg xmlns="http://www.w3.org/2000/svg" width="20" height="20">…</svg>',
            action(editor) {
                editor.insertText('> [!NOTE]\n> Something worth noting');
            },
        },
    }, 'preview'],
});
```

</Snippet>

The `title` is the tooltip and the CSS class, so that one is `.callout-btn`,
exactly like a built-in tool. Add as many as you like, each its own entry, each
with a distinct title — two tools sharing a title share a class, and one with
no title falls back to `.custom-btn`.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Property | Type | Purpose |
| --- | --- | --- |
| `title` | `string` | Required. Tooltip, CSS class, and the key `locale` translates. |
| `action` | `function` | Required. Gets `(editor, event)`. Pass the event on if you open a dialog. |
| `icon` | `string` | Inline SVG for the face of the button. |
| `shortcut` | `string` | e.g. `Ctrl+Shift+K`. Shown in the tooltip, and beats a built-in using the same keys. |

</DocTable>

A tool with no `action` is skipped with a console warning rather than breaking
the toolbar, and its shortcut is not registered either.

### Changing the document

Use `editor.insertText()` rather than writing to the textarea yourself. It
replaces the selection, restores focus, moves the caret, scrolls, re-renders the
preview and fires `onChange` — and undo keeps working, because the edit went
through the normal path.

<Snippet view="code">

```javascript
action(editor) {
    const textarea = editor.usertextarea;
    const selected = textarea.value.slice(textarea.selectionStart, textarea.selectionEnd);
    const wrapped = `==${selected || 'highlight'}==`;

    // (text, where the caret lands, characters to leave outside the selection)
    editor.insertText(wrapped, wrapped.length, 0);
}
```

</Snippet>

### A tool that waits on a server

A button that does nothing for two seconds reads as broken. Put something in the
document immediately and swap it when the answer arrives — the image upload
works exactly this way.

<Snippet view="code">

```javascript
async function rewrite(editor) {
    const textarea = editor.usertextarea;
    const selected = textarea.value.slice(textarea.selectionStart, textarea.selectionEnd);
    if (!selected.trim()) return;

    const token = `[${editor.label('Rewriting...')}]`;
    editor.insertText(token, token.length, 0);

    const put = (replacement) => {
        // Search for the token rather than remembering where it went: the
        // document keeps moving while the request is in flight, and it may
        // have been deleted altogether.
        const at = textarea.value.indexOf(token);
        if (at === -1) return;
        textarea.value = textarea.value.slice(0, at)
            + replacement + textarea.value.slice(at + token.length);
        textarea.setSelectionRange(at, at + replacement.length);
        editor.render();
        editor.notifyChange();
    };

    try {
        const response = await fetch('/api/rewrite', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ text: selected }),
        });
        if (!response.ok) throw new Error('HTTP ' + response.status);
        put((await response.json()).text);
    } catch (error) {
        put(selected);                      // put their paragraph back
        console.error('[rewrite] failed', error);
    }
}
```

</Snippet>

Four things there are worth copying whatever your tool does:

- **Insert a placeholder first**, swap it later.
- **Find it by searching**, not by remembering an offset.
- **Restore the original if the call fails.** Losing someone's paragraph to a
  failed request is the one outcome worth engineering against.
- **Put the waiting text through `editor.label()`**, so it translates with the
  rest of the interface.

That shape fits anything that waits: a translator, a spell check, a house-style
linter, a language model. The editor has no AI and no key of its own — the
endpoint is yours and the key stays on your server, where a browser cannot read
it.

### A tool with its own markup

A dropdown or a dialog cannot be described declaratively, so write a class.
Extend `MarkdownEditor.Tool`, set `this.button`, implement `applySyntax()`.

<Snippet view="code">

```javascript
class EmbedTool extends MarkdownEditor.Tool {
    constructor(editor) {
        super(editor, 'Embed video');        // tooltip, and .embed-video-btn
        this.shortcut = 'Ctrl+Shift+E';      // optional
        this.button = this.createButton('<svg>…</svg>');
    }

    applySyntax(event) {
        const dialog = MarkdownEditor.modal(event, 'fj:max-w-sm', `
            <input type="url" class="embed-url fj:me-input fj:w-full">
            <button type="button" class="embed-go fj:me-btn fj:me-btn-sm">Insert</button>
        `, 'Embed');

        dialog.querySelector('.embed-go').addEventListener('click', () => {
            const url = dialog.querySelector('.embed-url').value.trim();
            if (url) this.editor.insertText(`\n<iframe src="${url}"></iframe>\n`);
            dialog.close();
        });
    }

    destroy() {
        // editor.destroy() calls this. Release anything you registered.
    }
}

new MarkdownEditor('#notes', { toolbar: ['bold', EmbedTool, 'preview'] });
```

</Snippet>

Configuration goes as `{ tool: EmbedTool, config: {...} }` and arrives as the
constructor's second argument. `this.button = null` renders nothing, for a tool
that only applies sometimes. One thing to watch: `Tool`'s constructor calls
`createButton()`, so anything your override needs has to come from
`this.editor`, not from a field you assign after `super()`.

### What a tool inherits

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Helper | What it does |
| --- | --- |
| `this.trimSelection()` | Shrinks the selection off surrounding whitespace. Double-clicking a word takes the space after it, and `**word **` renders as nothing. Call it first. Line-based tools should not — a trailing newline is what tells them which lines are covered. |
| `this.editor.label(text)` | The translation, or the string itself. Use it for anything your tool shows. |
| `MarkdownEditor.modal(event, size, html, label)` | The dialog the link and image tools use, so yours looks like the rest. Returns the open `<dialog>`; close it with `dialog.close()`. Pass the event you were given — it finds the editor, inherits the theme, and cleans itself up. |
| `editor.renderMarkdown(md)` | HTML exactly as the preview makes it, honouring your `renderer` and `sanitizer`. |
| `editor.createToolbar(textarea, tools)` | A real toolbar bound to another textarea, for a dialog that collects rich text. Your `locale` is inherited; no preview button is added. |

</DocTable>

Custom tools translate like built-in ones, keyed on the title you gave:

<Snippet view="code">

```javascript
locale: { 'Callout': 'Aviso', 'Embed video': 'Insertar vídeo' }
```

</Snippet>

The class is unaffected, so `.callout-btn` stays `.callout-btn` in every
language.

## Draft recovery

A tab crashes, a laptop sleeps and never wakes, somebody closes the wrong
window. Whatever was typed and not submitted is gone, because the only copy was
in a textarea.

<Snippet view="code">

```javascript
new MarkdownEditor('#content', { autosave: true });
```

</Snippet>

**Try it:** type something below, reload this page, and it will offer the draft
back.

<RawHtml html={"<div class=\"not-prose my-5\" style=\"min-height:19rem\"><p class=\"mte-demo-label\">Live demo &mdash; type in it</p><textarea class=\"mte-autosave\" rows=\"6\" aria-label=\"Markdown editor demo with draft recovery\" placeholder=\"Type something, then reload the page...\"></textarea></div>"} />

### It never restores on its own

That is the part worth understanding. A draft is a second copy of the same
text, and two copies disagree sooner or later:

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| | |
| --- | --- |
| Monday | you type a draft, and it is stored |
| Monday | you submit, and the server saves it |
| Tuesday | somebody else edits the document, so the server is newer |
| Wednesday | you open the page, and the textarea has their text in it |

</DocTable>

An editor that restored automatically would put Monday's draft over Tuesday's
work and say nothing. So it offers instead: a strip above the toolbar, with how
long ago the draft was taken, and one button — **Review**.

### Review shows you the difference

The dialog holds the draft against what is on the page, line by line: what the
draft would take out, what it would put in, and a few lines either side to say
where in the document it happened. **Restore** and **Discard** live in there and
only in there, because both are irreversible and neither belongs on a bar that
appeared while you were reading something else.

Ignoring the strip costs nothing, which is the quick path. Closing it means
"not now" — the draft stays stored and is offered again next load.

### Both answers can be taken back

Restore or discard, and the strip says what happened and offers **Undo**. Undo
puts the draft back in storage either way, and after a restore it reverses the
document change as well. So neither click destroys anything: you end up where
you were before it.

A restore is also one undo step in the editor itself, so `Ctrl+Z` works on it
like any other edit.

### When the page has moved on

If the text on the page changed since the draft was taken, the strip says so.
That is the case where the draft is most likely to be the stale copy, and it is
the one the dialog is for.

### Where the draft is kept

`localStorage`, under a key built from the page's address and the field's `id`
or `name`. Two editors on one page are two drafts; the same document at two
addresses is two records, which is usually right.

<Snippet view="code">

```javascript
new MarkdownEditor('#content', {
    autosave: {
        key: 'post-42',               // say it yourself, where the address is not stable
        maxAge: 24 * 60 * 60 * 1000,  // dropped unread after a day. A week by default
        debounce: 1000,               // milliseconds after typing stops
    },
});
```

</Snippet>

Pass `key` where the address carries something incidental — a campaign
parameter, a session id — or where one record is edited at several URLs.

### What clears it

Submitting the form, restoring the draft, discarding it, or deleting your way
back to the text the page loaded with. A draft older than `maxAge` is dropped
unread.

### Things to know

- **Off unless you ask.** It writes what someone is typing to a disk this
  library does not own, on machines that are sometimes shared. That is the
  application's call, not a default.
- **`localStorage` holds about 5 MB per origin**, shared with everything else
  your app keeps there, and counted in UTF-16. A draft past roughly 2.5 million
  characters is refused — the console says so, once, and your text is never at
  risk, because the textarea is the document.
- **It is not a backup.** It survives a crash, not a cleared browser, and it
  never leaves the machine.

## Pasting formatted text

Copy a few paragraphs from a web page, a wiki or a word processor, paste them
in, and the headings, links, lists and tables arrive as markdown.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Pasted | Becomes |
| --- | --- |
| Headings | `#` to `######` |
| Bold, italic, strikethrough | `**`, `*`, `~~` |
| Links and images | `[text](url)`, `![alt](src)` |
| Lists, nested to any depth | `-` and `1.`, indented |
| Code, inline and block | backticks, with the language where the source says |
| Blockquotes, rules, tables | `>`, `---`, pipe tables |

</DocTable>

Markdown characters in the pasted prose are escaped, so a sentence with an
asterisk in it stays a sentence.

The conversion declines more often than it acts. Where the clipboard carries no
formatting worth keeping, or the result would match the plain text anyway, the
browser does its own paste and keeps its own undo entry. Pasted HTML goes
through the same sanitizer as the preview, so a page carrying a script tag loses
it on the way in.

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', { pasteHtml: false });   // always paste plain
```

</Snippet>

### A URL pasted over a selection becomes a link

Select some text, paste a URL over it, and you get the link rather than the URL
replacing what you selected.

<Snippet view="code">

```markdown
Read the docs                        <- select "the docs", paste https://example.com
Read [the docs](https://example.com) <- what you get
```

</Snippet>

Deliberately strict: only a bare `http` or `https` URL with no whitespace in it.
Pasting a sentence that happens to contain a URL, or pasting with nothing
selected, is an ordinary paste.

## Maths

Add `math` to the toolbar. The button, or `Alt+M`, wraps the selection in TeX
delimiters — `$...$` on one line, `$$...$$` across several. Press again to take
them off.

The editor writes the delimiters and nothing else. **It does not render TeX**,
because maths is not part of markdown and a TeX engine is several times the size
of the whole editor. What you get is portable markdown that GitHub, Obsidian and
Jupyter all render.

To see it in the preview, bring a renderer and its stylesheet:

<Snippet view="code">

```javascript
import markdownIt from 'markdown-it';
import katex from '@vscode/markdown-it-katex';
import 'katex/dist/katex.min.css';

new MarkdownEditor('#notes', {
    toolbar: ['bold', 'italic', 'math', 'preview'],
    renderer: md => markdownIt().use(katex).render(md),
});
```

</Snippet>

Without one the preview shows `$x^2$` as written, and the console says so once
rather than leaving you wondering whether the button worked.

## Uploading files

A file reaches the editor three ways — the image button's picker, a pasted
screenshot, and a file dropped on the textarea. `upload` is where all three go.

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', { upload: '/api/upload' });
```

</Snippet>

That is the whole configuration for the common case: your endpoint gets the file
as `multipart/form-data` and answers with a URL.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Written as | Use it when |
| --- | --- |
| `upload: '/api/upload'` | Your endpoint answers with a URL. Most hosts. |
| `upload: { url, ... }` | You need a CSRF header, a size limit, types past images, or your endpoint answers in its own shape. |
| `upload: async (file, alt) => url` | You do the request yourself: a presigned PUT, an upload library, anything the options cannot describe. |

</DocTable>

<div class="accordion-content">

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Property | Type | Default | Purpose |

| `accept` | `string[]` | `['image/*']` | What may be uploaded, as `'png'`, `'image/png'` or `'image/*'`. Decides what the editor will even look at: a type outside the list is left alone on paste and drop. |
| `maxSize` | `number` | no limit | Largest file, in bytes. Unlike `accept`, going over it is reported — the file was one you said you would take. |
| `insert` | `function` | see below | The markdown written once it lands. Gets `(file, url, alt)`. |
| `onProgress` | `function` | — | `(file, loaded, total)` as the bytes go out, for a progress bar of your own. |
| `paste` | `boolean` | `true` | `false` leaves pasted files alone. |
| `drop` | `boolean` | `true` | `false` refuses dropped files. The drop is still swallowed — letting it through hands the file to the browser, which navigates away and takes the unsaved document with it. |

</DocTable>

The alt text always travels as `image_alt`, whatever `field` says. There is no
option for it on purpose: an endpoint that cannot read `image_file` because it
already exists under another name can still read a string called `image_alt`.

</div>
</details>
</div>

### Paste and drop

Both go to the same endpoint as the button. A placeholder appears at once so the
editor never looks frozen, and it is replaced when the upload lands. If it
fails, the placeholder becomes a visible marker rather than vanishing — which
without devtools open would look like nothing happened.

Several files at once go up one at a time, so they land in the order they
arrived.

Uploading needs no image button at all:

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', {
    toolbar: ['bold', 'italic', 'link', 'preview'],   // no image tool
    upload: '/api/upload',
});
```

</Snippet>

What that gives up is the dialog: no way to insert an image by typing a URL, and
no alt field, so `image_alt` always arrives empty.

With no `upload` configured, pasting a file does nothing and the console says
what to add. A dropped file is swallowed all the same, for the reason above.

### What lands in the document

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Uploaded | Inserted |
| --- | --- |
| an image | `![alt](url)` |
| a video | `<video src="url" controls></video>` |
| audio | `<audio src="url" controls></audio>` |
| anything else | `[filename](url)` |

</DocTable>

Markdown has syntax for exactly one of those. Video and audio are raw HTML
because there is nothing else to write, and anything else is a link named after
the file — which is what every forum and issue tracker does with an attachment.

Images are all that is accepted until you say otherwise:

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', {
    upload: {
        url: '/api/upload',
        accept: ['image/*', 'video/mp4', 'application/pdf'],
        maxSize: 50 * 1024 * 1024,
    },
});
```

</Snippet>

Writing HTML for a video is a bet that whatever renders this markdown allows it
through. Most pipelines do; `markdown-it` with `html: false` and
Python-Markdown do not, and there a reader sees the tag as text. Give `insert`
where that is true of yours:

<Snippet view="code">

```javascript
insert: (file, url, alt) => file.type.startsWith('video/')
    ? `[${file.name}](${url})`          // a link, because our renderer escapes HTML
    : `![${alt || ''}](${url})`,
```

</Snippet>

### What your endpoint receives

A `POST` as `multipart/form-data`, carrying `image_file` (or whatever `field`
names), `image_alt`, anything in `params`, and anything in `headers` as headers.

Answer with a URL. Any of these is understood with no configuration:

<Snippet view="code">

```json
{ "url": "https://cdn.example.com/uploads/a.webp" }
{ "path": "/uploads/a.webp", "alt": "Two people looking at a laptop" }
{ "success": true, "image_path": "/uploads/a.webp", "image_alt": "optional" }
{ "success": false, "error": "The disk is full" }
```

</Snippet>

`url` and `path` are read first. `image_path` is the contract 1.8 shipped with
and still works, but an endpoint that stores PDFs should not have to call its
answer that. `alt` is a suggestion, used only where the user left the field
empty, so a server that derives alt text can offer it without overwriting a real
description.

```python
import uuid
from pathlib import Path

from django.contrib.auth.decorators import login_required
from django.core.files.storage import default_storage
from django.http import JsonResponse
from django.views.decorators.http import require_POST

ALLOWED   = {".jpg", ".jpeg", ".png", ".webp"}
MAX_BYTES = 5 * 1024 * 1024


def fail(message):
    # 200, not 4xx: the editor reads the status before the body
    return JsonResponse({"success": False, "error": message})


@login_required
@require_POST
def upload(request):
    file = request.FILES.get("image_file")
    if file is None:
        return fail("No file was sent.")

    suffix = Path(file.name).suffix.lower()
    if suffix not in ALLOWED:
        return fail("That file type is not allowed.")
    if file.size > MAX_BYTES:
        return fail("That file is over 5 MB.")

    saved = default_storage.save(f"uploads/{uuid.uuid4().hex}{suffix}", file)

    return JsonResponse({
        "url": default_storage.url(saved),
        "alt": request.POST.get("image_alt", ""),
    })
```

## Interface language

The editor's own words — tooltips, menus, dialog fields, buttons — are English
by default. `locale` translates them, keyed on the English string the way
gettext works, so you list only what you want to change and anything missing
stays English.

<Snippet view="code">

```javascript
import es from 'markdown-text-editor/locale/es';

new MarkdownEditor('#notes', { locale: es });
```

</Snippet>

Fifty-six languages ship, under `markdown-text-editor/locale/`. Import the one
you want and only that one reaches your bundle.

**They are machine-translated and have not been checked by native speakers.**
Each file says so of itself — it exports `reviewed`, `false` everywhere for now
— so you can decide whether to vet one before shipping it. Every file is checked
against the English template on each release for missing keys and lost `{n}`
placeholders, so what is wrong with any of them is wording rather than wiring.
Corrections are the fastest contribution to make.

`locale` takes the strings, not a language code: `locale: 'es'` does nothing and
says so in the console.

### Part of a language, or your own wording

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', {
    locale: {
        'Bold': 'Gras',
        'Italic': 'Italique',
        'Link': 'Lien',
        'Alt text': 'Texte alternatif',
        'Uploading...': 'Téléversement...',
        '{n} words': '{n} mots',      // {n} is where the number goes
    },
});
```

</Snippet>

All 78 strings ship as a template, so you do not have to go looking:

<Snippet view="code">

```javascript

// { "Bold": "Bold", "Match case": "Match case", "{n} words": "{n} words", ... }
```

</Snippet>

Already have a translation system? Feed the editor from it, and the wording

</Snippet>

## Custom renderer

The preview uses [marked](https://marked.js.org) and
[DOMPurify](https://github.com/cure53/DOMPurify). Swap either one.

<Snippet view="code">

```javascript
import markdownIt from 'markdown-it';
import footnote from 'markdown-it-footnote';

new MarkdownEditor('#notes', {
    renderer: md => markdownIt({ html: false, linkify: true }).use(footnote).render(md),
});
```

</Snippet>

Markdown in, HTML out. The result still goes through the sanitizer, so a
renderer with `html: true` is no less safe than the default.

<Snippet view="code">

```javascript
import DOMPurify from 'dompurify';

new MarkdownEditor('#notes', {
    // keep the sanitizer, tighten it
    sanitizer: html => DOMPurify.sanitize(html, { FORBID_ATTR: ['style'] }),
});
```

</Snippet>

Two things to know. A renderer that **throws** does not take the editor with it:
the preview falls back to escaped plain text, says so once in the console, and
the document is untouched. And the preview's clickable checkboxes come from the
renderer's output — if yours emits no `<input type="checkbox">` for `- [ ]`, the
console tells you which plugin to add.

## Content security policy

No inline event handlers, no `eval`, and from 2.0 no injected `<style>`. A
strict policy needs no exception for the editor in either direction:

<Snippet view="code">

```
Content-Security-Policy: script-src 'self'; style-src 'self'
```

</Snippet>

Before 2.0 the CSS was carried in the JavaScript and injected at load, which a
policy without `style-src 'unsafe-inline'` refuses
([#42](https://github.com/nezanuha/markdown-text-editor/issues/42)). A nonce was
considered and dropped: it only helps policies that have one, and a statically
hosted site on `style-src 'self'` has no server minting a fresh nonce per
request. Linking the stylesheet covers every policy instead of some.

One thing the editor does not control is the markdown your users write.
DOMPurify keeps `style` attributes, so `<span style="color:red">` in a document
survives into the preview and a strict `style-src-attr` will report it. Strip
them with `sanitizer` if that matters to you.

## Accessibility

Built in, not configured. If you are evaluating the editor against a
standard, this is the list.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| | |
| --- | --- |
| **The toolbar is one tab stop** | Arrow keys move along it, `Home` and `End` jump to the ends. It used to cost nineteen presses of `Tab` to get past. The arrows follow the text direction, so they mirror in Arabic and Hebrew. |
| **Every button announces its shortcut** | "Bold (Ctrl+B)", in the accessible name as well as the tooltip, so nobody has to see a tooltip to learn one. |
| **State is reported, not just drawn** | `aria-pressed` on the preview toggle and on each find switch. A dimmed tool carries `aria-disabled` rather than `disabled`, so it stays in the tab order and a screen reader can still cross the bar it was reading. |
| **The field has a name in your language** | A textarea with a `<label>`, an `aria-label` or an `aria-labelledby` is left alone. Without one the editor supplies a name, and it goes through `locale` like everything else — a Spanish editor does not read "Markdown editor". |
| **Dialogs behave like dialogs** | The link and image dialogs are real `<dialog>` elements with their own accessible names, and focus returns to where it came from on close. |
| **The find panel is a landmark** | A labelled `search` region. Shortcuts are in `aria-keyshortcuts`, the arrows go disabled when there is nothing to move to, and the match count is spoken once you stop typing rather than interrupting itself on every keystroke. |
| **Icons are hidden from screen readers** | Every SVG is `aria-hidden`, because the button already has a name. |
| **Notices are announced** | The draft strip is a `role="status"` region, so it is read without stealing focus from what you were typing. |
| **Motion is dropped on request** | `prefers-reduced-motion: reduce` turns off every transition and animation inside the editor. Nothing that moves in it carries meaning the end state does not. |
| **Contrast is checked** | The dimmed markdown markers in hybrid mode read at 4.54:1 against the light theme. Interface parts are asked for 3:1. |

</DocTable>

Right-to-left needs no option. The editor reads the direction from the page
and lays itself out accordingly — the toolbar, the find panel, the preview
split, the variables menu and the table bar all mirror. What it cannot do is
translate itself, so pass a [`locale`](#interface-language) as well: a toolbar
reading "Bold" over right-to-left text is only half done.

## What it does to stay quick

A keystroke costs about the same in a long document as a short one, which
took some doing.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| | |
| --- | --- |
| **Hybrid redraws only what changed** | A line whose text and fence state are both unchanged keeps the markup it already had. Re-highlighting the whole document on every keystroke is what made long files crawl. |
| **It measures itself rarely** | Reading an element height makes the browser lay out the page first. The editor only measures when the text gets shorter or its width changes. At 150,000 characters that took a keystroke from about 220ms to about 5ms. |
| **The preview is debounced, and skipped while closed** | Parsing and sanitising a whole document into a pane nobody can see is work thrown away. It renders when it is open. |
| **Undo stores what changed** | One span per step — where the change starts, what was there, what is there now — rather than a copy of the document or a character-level diff of it. A 5,000-character paste into 100,000 characters costs 0.4ms. |
| **Find stops drawing past 400 matches** | Only the current one is marked, so a document full of a common word stays responsive. |
| **The preview scrolls by ratio** | No layout thrash on either side while you scroll. |

</DocTable>

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Download | Gzipped |
| --- | --- |
| `<script src>`, marked and DOMPurify inside it | 57 kB JS + 16 kB CSS |
| Through a bundler, which resolves those two itself | 34 kB JS + 16 kB CSS |

</DocTable>

The stylesheet is cached separately from the script, so a CSS-only release
does not re-download the JavaScript and vice versa.
## Reading and writing content

The textarea is the field. That is the whole API.

<Snippet view="code">

```javascript
const field = document.getElementById('notes');

field.value;                    // the markdown, correct at every moment
field.value = '# New content';  // set it
new FormData(form).get('content');   // works, because it is a real field
```

</Snippet>

Writing to `.value` directly does not notify the editor, which matters in
hybrid mode and for the preview. Either use `insertText`, or tell it:

<Snippet view="code">

```javascript
field.value = '# New content';
editor.render();          // redraw the formatting layer and the preview
editor.notifyChange();    // and fire onChange
```

</Snippet>

Server-rendered content needs nothing special — put it in the textarea and the
editor picks it up:

<Snippet view="code">

```html
<textarea id="notes" name="content">{{ post.content }}</textarea>
```

</Snippet>

### Reacting to changes

<Snippet view="code">

```javascript
new MarkdownEditor('#notes', {
    onChange: (markdown) => {
        document.querySelector('#count').textContent = markdown.length;
    },
});
```

</Snippet>

Fired for everything that changes the document: typing, toolbar actions, undo
and redo, list continuation, a restored draft, a pasted document, a replace.
Debounce it yourself if it does anything expensive.

### Tearing it down

<Snippet view="code">

```javascript
editor.destroy();
```

</Snippet>

Puts your textarea back where it was with its content and its classes intact,
removes every listener, and releases the dialogs, the find panel, the draft
timer and the fullscreen lock. Call it before you remove the element from the
DOM — in a React cleanup, a Vue `onBeforeUnmount`, or a Turbo teardown.

Create it in an effect, destroy it on cleanup. Use `defaultValue`, not `value`:
the editor writes to the textarea directly, so a controlled binding would
overwrite what is being typed.

<Snippet view="code">

```javascript
import { useEffect, useRef } from 'react';
import MarkdownEditor from 'markdown-text-editor';

function MarkdownField({ name, defaultValue = '', onChange }) {
    const ref = useRef(null);

    // Options are read once, so the editor would hold on to whichever
    // onChange it was handed first. A ref keeps it current.
    const onChangeRef = useRef(onChange);
    onChangeRef.current = onChange;

    useEffect(() => {
        const editor = new MarkdownEditor(ref.current, {
            onChange: (value) => onChangeRef.current?.(value),
        });
        return () => editor.destroy();
    }, []);

    return <textarea ref={ref} name={name} defaultValue={defaultValue} />;
}
```

</Snippet>

The cleanup also covers StrictMode, which runs effects twice in development and
would otherwise leave two editors on one textarea. The empty dependency array is
deliberate: options are read once, so re-running the effect would tear the
editor down and rebuild it on every render.

</div>

```javascript
import { ref, onMounted, onBeforeUnmount } from 'vue';
import MarkdownEditor from 'markdown-text-editor';

const el = ref(null);
const props = defineProps({ modelValue: { type: String, default: '' } });
const emit = defineEmits(['update:modelValue']);
let editor = null;

onMounted(() => {
    el.value.value = props.modelValue;         // set it once
    editor = new MarkdownEditor(el.value, {
        onChange: value => emit('update:modelValue', value),
    });
});

onBeforeUnmount(() => editor?.destroy());
```

</Snippet>

Do not bind `:value`, or every keystroke emitted back through `v-model` would
overwrite the textarea. In a plain form you can skip `v-model` and read the
value on submit, as with any other framework.

SvelteKit need no `dynamic(..., { ssr: false })` wrapper. The editor is created
inside `useEffect` or `onMounted`, and neither runs on the server.

The textarea ships in the server HTML with its content already in it, so there
is nothing to wait for and nothing that pops in. React renders the same markup
on both sides and the editor enhances it after hydration — no mismatch warning.

## Upgrading from 1.x

One line has to change, and it is the stylesheet. Everything else that was
renamed in 2.0 still answers to its old name.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| What changed | What to do |
| --- | --- |
| **The CSS is a separate file.** It used to be injected as a `<style>` tag. | Add the stylesheet, once per page. Nothing renders correctly until you do, and the console says so. |
| `dist/markdown-text-editor.umd.js` is gone. | It is `dist/markdown-text-editor.cjs`. Only a path that reached past the package for that filename is affected; `import` and `require` resolve on their own. |
| `labels` became `locale`. | Nothing, today. Both work. |
| `label` is deprecated. | Nothing, today. An `aria-label` or a `<label for>` on the textarea does the same natively, and the editor already prefers either. |
| `{ image: { fileInput: { uploadUrl } } }` became top-level `upload`. | Move it when you can: this is the one of the four that will be removed, in a future major version, because it cannot upload from a paste or a drop. |
| `{ variables: [...] }` in the toolbar became top-level `variables`. | Nothing, today. |
| Uploads go out over `XMLHttpRequest` instead of `fetch`. | Nothing, unless a test stubs `fetch` to catch an upload. Same body, same credentials, same errors — `fetch` just cannot report progress. |

</DocTable>

Each of these says so once in the console the first time the editor sees it,
naming the replacement.

<Snippet view="code">

```javascript
// with a bundler, once, anywhere in your entry
import 'markdown-text-editor/style.css';
```

</Snippet>

<Snippet view="code">

```html
<!-- or in the page, next to the script tag -->
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/markdown-text-editor@2/dist/markdown-text-editor.css">
```

</Snippet>

## What the console might tell you

It never fails silently at something you can fix.

<div class="accordion my-6">
<details name="ref-console">
<summary>Every message, and what it means</summary>
<div class="accordion-content">

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Message starts with | What happened |
| --- | --- |
| *Stylesheet not loaded* | The CSS is a separate file from 2.0. Link it or import it. The editor works, it just looks unstyled. |
| *locale: '...' has no effect* | `locale` takes the strings, not a language code. Import the one you want. |
| *toolbar takes an array of tools* | Something other than an array, e.g. `toolbar: 'bold'`. The default is used instead. |
| *toolbar: no tool matches* | A name in the array is not a tool. Check it against [the tools](#the-tools); the entry is skipped. |
| *A custom tool needs an action function* | A `{ custom: {...} }` entry has no `action`. It renders no button. |
| *heading levels must be an array* | `{ heading: { levels } }` got something else. All six are offered. |
| *Ignored heading levels outside 1-6, or repeated* | One of the levels was out of range or listed twice. The rest are used. |
| *No usable heading levels* | Nothing in `levels` could be used, so the dropdown falls back to all six rather than rendering empty. |
| *Maths syntax found, but nothing rendered it* | Pass a `renderer` that understands TeX, and load its stylesheet. |
| *Task list syntax found, but the custom renderer emitted no checkbox* | Your `renderer` does not handle `- [ ]`. The preview's checkboxes come from its output. |
| *The renderer threw* | Yours, or the default one, failed on this document. The preview falls back to plain text; what you typed is untouched. |
| *A file was pasted / dropped but no upload endpoint is configured* | Pass `upload`. The drop is swallowed either way, so the unsaved document survives it. |
| *Could not convert the pasted HTML* | The rich-paste conversion threw, so the clipboard's plain text went in instead. Nothing is lost. |
| *autosave has no id or name to key the draft on* | The draft is keyed to the field's position on the page instead. Add a textarea above it and two drafts change places. Give the textarea an `id`, or pass `autosave: { key }`. |
| *autosave could not write the draft* | The document is past what `localStorage` will take, or the browser is refusing it. Your text is fine; the draft is not being kept. |
| *image.fileInput still works, and will be removed* | The pre-2.0 form, said once. The one deprecation that will go. |
| *labels is now locale* / *label is an aria-label* / *variables moved from the toolbar array* | Renamed in 2.0, each said once. Nothing is broken and nothing is going away. |
| *Image upload failed* | The endpoint answered with an error. The placeholder is marked in the text. |
| *Upload refused:* | A file failed the `accept` or `maxSize` check. What follows the colon is the MIME type or the byte count — the writer sees the translated message, you get the specifics. |

</DocTable>

## How it compares

Most JavaScript markdown editors — EasyMDE, SimpleMDE, anything built on
CodeMirror — hide your textarea and edit a copy, writing back on submit. That
works until something else needs the value.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| | MarkdownEditor | EasyMDE / SimpleMDE |
| --- | --- | --- |
| Your textarea | Still the field you type in | Hidden, edited as a copy |
| `required` fields | Work | The browser cannot focus a hidden field, so the submit is blocked |
| `.value` before submit | Correct, always | Empty until the form submits |
| `FormData`, htmx, Turbo | Work | Need the editor's own API |
| Hybrid WYSIWYG | Yes | No |
| Find and replace | Built in | No |
| RTL | Built in | Via CodeMirror's `direction` |
| Inline handlers (CSP) | None | Some |
| Dark mode | Four themes, inherited | Limited |
| Size, gzipped | 72 kB with a `<script>` tag, 49 kB through a bundler | 107 kB |

</DocTable>

The rest of this page is the consequence of that one decision. There is no
`getValue()` because `.value` already works, no sync step because there is
nothing to sync, and no framework wrapper because a textarea needs none.
