A markdown editor that enhances your textarea instead of replacing it, so form submission, validation and required fields keep working. WYSIWYG and plain Markdown modes, live preview, find & replace, RTL support, dark mode. Works standalone with Django, Laravel, Rails, Node.js, PHP, and any stack.

**No Frutjam and no Tailwind required.** The styles are bundled, so the editor drops into any project.

## Installation

#### NPM (bundlers: Vite, webpack, Rollup, etc.)

```bash
npm install markdown-text-editor
```

</Snippet>

The stylesheet is a separate file from 2.0.0. Import it **or** link it, never both. If you forget it entirely the editor still works and tells you what to add in the console, rather than rendering unstyled with no explanation.

TypeScript definitions ship with the package, so options, toolbar entries and variable shapes are checked and autocompleted with no extra install.

The types are importable too, which matters whenever your options are not written inline at the call site. TypeScript only checks for unknown keys on an object literal passed directly, so a config kept in its own variable has a misspelled key silently ignored. Annotating it puts the check back.

<Snippet view="code">

```typescript
import MarkdownEditor, { type MarkdownEditorOptions, type ToolbarEntry } from 'markdown-text-editor';

// Without the annotation this compiles, the editor renders with the default
// toolbar, and nothing tells you why.
const config: MarkdownEditorOptions = {
    placeholder: 'Write...',
    toolbr: ['bold', 'preview'],   // Error: did you mean to write 'toolbar'?
};

// Building a toolbar conditionally
const toolbar: ToolbarEntry[] = ['bold', 'italic'];
if (canUpload) toolbar.push('image');
toolbar.push('preview');
```

</Snippet>

The same applies to a wrapper component, where `MarkdownEditorOptions` is what you forward instead of `any`, so whoever uses your wrapper keeps the checking.

## The Philosophy: "Native-First"

Most editors break the standard web workflow. **MarkdownEditor** embraces it. Because it sits directly on top of a `<textarea>`, you don't need to learn a new way to handle data.

-   **No Data Binding Needed:** Works with `<form method="POST">` out of the box
-   **Standard Access:** Use `document.getElementById('editor').value` just like a normal input.
-   **Backend Agnostic:** Works with any backend (Python, Node.js, PHP, etc.) just like a normal form field

## MarkdownEditor vs EasyMDE / SimpleMDE

Most JavaScript markdown editors (EasyMDE, SimpleMDE, CodeMirror-based editors) **hide your `<textarea>`** and edit a copy, writing the content back when the form is submitted. That works until something else needs the value: a `required` field the browser cannot focus blocks the submit entirely, and `.value` or `FormData` read before submit returns an empty string, which breaks htmx, Turbo, autosave and unsaved-changes guards. **MarkdownEditor is different.** It styles the textarea you already have and leaves it as the field you type into, so the value is correct at every moment.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Feature | MarkdownEditor | EasyMDE / SimpleMDE |
| --- | --- | --- |
| Native textarea preserved | ✅ | ❌ Hidden, edited as a copy |
| Works with `required` fields | ✅ | ❌ Browser blocks the submit |
| `.value` correct before submit | ✅ | ❌ Empty until the form submits |
| Serialises with `FormData`, htmx, Turbo | ✅ | ❌ Needs the editor's own API |
| WYSIWYG hybrid mode | ✅ | ❌ |
| Built-in Find & Replace | ✅ | ❌ |
| RTL support | ✅ Built in | Via CodeMirror's `direction` option |
| Inline event handlers (CSP) | ✅ None | Some |
| Dark mode / theming | ✅ | Limited |
| Bundle size, gzipped | 52 KB JS + 14 KB CSS via `<script>`, 30 KB JS + 14 KB CSS via a bundler | 107 KB (JS + CSS) |

</DocTable>

## Framework Integration

Because **MarkdownEditor** preserves the native `<textarea>`, it integrates with every backend framework without any extra code. Your server receives the markdown content exactly as it would from any standard form field. For React and Vue it takes a few lines, covered at the end of this section.

### Django

Add a `class` to your textarea widget and initialize the editor: `request.POST['content']` works with no extra steps.

<Snippet view="code">

```python
    class Meta:
        model = Post
        fields = ['content']
        widgets = {
            'content': forms.Textarea(attrs={'class': 'markdown-editor'}),
        }
```

</Snippet>

```javascript
new MarkdownEditor('.markdown-editor');
// request.POST['content'] contains the markdown on submit
```

</Snippet>

### React

Create the editor in an effect and destroy it on unmount. Use `defaultValue` rather than `value`: the editor writes to the textarea directly, so a controlled binding would overwrite what the user is typing.

<Snippet view="code">

```javascript
import { useEffect, useRef } from 'react';
import MarkdownEditor from 'markdown-text-editor';

function MarkdownField({ name, defaultValue = '', onChange }) {
    const ref = useRef(null);

    // Options are read once at construction, so the editor would hold on to
    // whichever onChange it was handed first. A ref keeps it current.
    const onChangeRef = useRef(onChange);
    onChangeRef.current = onChange;

    useEffect(() => {
        const editor = new MarkdownEditor(ref.current, {
            onChange: (value) => onChangeRef.current?.(value),
        });
        return () => editor.destroy();
    }, []);

    return &lt;textarea ref={ref} name={name} defaultValue={defaultValue} /&gt;;
}
```

</Snippet>

Returning `editor.destroy()` from the effect also covers StrictMode, which runs effects twice in development and would otherwise leave two editors on one textarea. The empty dependency array is deliberate: options are read once when the editor is created, so re-running the effect would tear it down and rebuild it on every render.

That is also why `onChange` goes through a ref. Passing it straight into the constructor would pin the editor to whichever function it received on mount, and an inline arrow in the parent would go stale the moment anything it closes over changes.

### Vue

Same idea. Set the initial value once in `onMounted` and do not bind `:value`, or every keystroke emitted back through `v-model` would overwrite the textarea.

<Snippet view="code">

```javascript
&lt;script setup&gt;
import { ref, onMounted, onBeforeUnmount } from 'vue';
import MarkdownEditor from 'markdown-text-editor';

const el = ref(null);
const props = defineProps({ modelValue: { type: String, default: '' } });
const emit = defineEmits(['update:modelValue']);
let editor = null;

onMounted(() => {
    el.value.value = props.modelValue;
    editor = new MarkdownEditor(el.value, {
        onChange: value =&gt; emit('update:modelValue', value)
    });
});

onBeforeUnmount(() =&gt; editor?.destroy());
&lt;/script&gt;

&lt;template&gt;&lt;textarea ref="el"&gt;&lt;/textarea&gt;&lt;/template&gt;
```

</Snippet>

Used as `<MarkdownField v-model="content" />`. In a plain form you can skip `v-model` entirely and read the value from the textarea on submit, as with any other framework.


### Server-side rendering

Importing the editor on the server does not throw, so Next.js, Remix, Nuxt and SvelteKit need no `dynamic(..., { ssr: false })` wrapper around it.

The reason it works is the rule above: the editor is created inside `useEffect`, `onMounted` or `onMount`, and none of those run on the server. The DOM work stays in the browser.

<Snippet view="code">

```javascript
// app/page.tsx — a server component, nothing opted out of SSR
import MarkdownField from './MarkdownField';

export default function Page() {
    return (
        <form method="post">
            <MarkdownField name="content" defaultValue="# Hello" />
        </form>
    );
}
```

</Snippet>

The `<textarea>` ships in the server HTML with its content already in it, so there is nothing to wait for and nothing that pops in. React renders the same markup on both sides and the editor enhances it after hydration, so there is no mismatch to warn about.

## Configuration

You can fully customize the editor's behavior and interface by passing an `options` object. If you omit an option, the **default** value is used.

Options are read once, when the editor is constructed. Changing them afterwards has no effect: call `destroy()` and create a new editor instead.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Property | Type | Default | Purpose |
| --- | --- | --- | --- |
| `mode` | `string` | `'plain'` | Sets the initial view. Use hybrid for a WYSIWYG experience or plain for raw syntax. |
| `placeholder` | `string` | `'Write your markdown...'` | Text shown when the editor is empty. Not applied if the textarea carries a `placeholder` of its own. |
| `toolbar` | `array` | every tool that needs no setup | Defines which tools appear and in what order. Passing it replaces the whole set rather than adding to it. The default is listed under [Toolbar Customization](#toolbar-customization). |
| `footer` | `boolean \| object` | all but `words` | Controls the status bar shown below the editor. Set to `false` to hide it entirely, or pass an object to toggle individual stats. |
| `find` | `boolean` | `true` | Find and replace, opened with `Ctrl+F`. Set `false` to leave that shortcut to the browser. |
| `tableBar` | `boolean` | follows the toolbar | The controls that open beside a table when you click inside one, or on `Alt+T`. Omit it and they come with the `table` tool. Set `true` to offer them without that tool, for content that already holds tables; `false` to edit the pipes by hand. `Tab` between cells works either way. |
| `pasteHtml` | `boolean` | `true` | Converts formatted text pasted from a web page or a word processor into markdown, instead of dropping to plain text. Set `false` to always paste plain. |
| `autosave` | `boolean \| object` | `false` | Keeps a draft of what is being typed in the browser and offers it back after a crash. Off by default, because it writes to a disk this library does not own. The object form takes `key` (what identifies this draft, in place of the page address and the field's `id`), `maxAge` (milliseconds before a draft is dropped unread, a week by default) and `debounce` (milliseconds after typing stops before it saves, `1000` by default). |
| `variables` | `array \| object` | — | The placeholders your users insert rather than type. The array is the list; the object form is `` `{ items, complete }` ``, where `complete` turns off completing as you type. Put `'variables'` in `toolbar` for the dropdown; the list is read whether or not the button is there, because the preview uses its sample values. |
| `upload` | `string \| object \| function` | — | Where uploaded files go, used by the image dialog, by pasting and by dropping alike. See [Uploading Files](#uploading-files). |
| `theme` | `string` | inherited | Explicitly sets the editor theme (light, dark, snowberry, darkberry). If omitted, the editor inherits `data-theme` from the nearest ancestor element or the `<textarea>` itself. |
| `minHeight` | `number` | `200` | Minimum height in pixels the editor will shrink to when content is short. Pairs with `maxHeight` to set the auto-grow range. |
| `maxHeight` | `number` | `500` | Maximum height in pixels the editor can grow to in non-fullscreen mode. Once content exceeds this height a scrollbar appears inside the editor. The editor also has a drag handle so users can manually resize it beyond this limit. |
| `renderer` | `function` | `marked` | Replaces the markdown parser used for the preview. Receives the markdown string and must return an HTML string. |
| `sanitizer` | `function` | `DOMPurify` | Replaces the HTML sanitizer. Receives the rendered HTML and must return the safe HTML to display. |
| `onChange` | `function` | `undefined` | Callback fired on every content change: typing, toolbar actions, undo/redo, and list continuation. Receives the current markdown string as its only argument. |
| `locale` | `object` | `undefined` | Translations for the editor's own interface, keyed by the English string. Anything you leave out stays in English. |

</DocTable>

Each feature the editor offers that is not a toolbar button has one option
named after it: pass `false` to turn it off, or an object to configure it where
there is anything to configure.

<Snippet view="code">

```javascript
const editor = new MarkdownEditor('#editor', {
    toolbar: ['bold', 'italic', 'table', 'preview'],
    find: true,
    tableBar: true,
    footer: { words: true },
});
```

</Snippet>

### 🛠 Toolbar Customization

The toolbar is modular. You can create a minimal experience or a full-featured power suite by modifying the array.

#### What you get by default

Leave `toolbar` out and you get every tool that works without setting anything
up, in this order:

<Snippet view="code">

```javascript
// The default toolbar, written out. Leaving `toolbar` off gives you exactly this.
toolbar: [
    'undo', 'redo',
    'heading', 'blockquote',
    'ul', 'ol', 'checklist', 'outdent', 'indent',
    'bold', 'italic', 'strikethrough', 'code',
    'codeblock', 'hr', 'table',
    'link', 'image',
    'preview',
]
```

</Snippet>

Two tools are **not** in that list, because neither can work until you supply
something:

- **`math`** needs a `renderer` that understands TeX. The editor does not render
  maths itself, so on a default toolbar the button would insert `$x^2$` and the
  preview would show the dollar signs as written.
- **`variables`** needs your own list of placeholders. Nobody else can supply
  it, and with nothing configured the tool adds no button at all.

That is the rule for every tool, including any added later: **on by default if
it needs no configuration, opt-in if it does.**

#### Passing `toolbar` replaces the set

It is not added to the default, it is used instead of it. So a list you write
out stays exactly as written, and will not gain tools added to the default in a
later version. That is deliberate — a toolbar curated down to five buttons
should not grow new ones on its own — but it means **if you want the defaults,
leave the option out** rather than copying the list above.

#### Heading levels

The `heading` dropdown offers H1 to H6. Where H1 belongs to the page rather than the content, which is the case for most CMS body fields, narrow it:

<Snippet view="code">

```javascript
new MarkdownEditor('#markdown-editor', {
    toolbar: [{ heading: { levels: [2, 3, 4] } }, 'bold', 'italic', 'preview']
});
```

</Snippet>

`Ctrl+1`, `Ctrl+2` and `Ctrl+3` follow the same list, so a level you leave out cannot be inserted from the keyboard either, and the button's tooltip lists only the shortcuts that still work. The order you write them in does not matter, the menu is always H1 first. Levels outside 1 to 6 are ignored with a console warning, and a list with nothing usable in it falls back to all six rather than rendering an empty menu.

This restricts the toolbar, not the document. Someone can still type `# Title` by hand and it renders as a heading, because what is valid markdown is the renderer's decision rather than the toolbar's. If the rule has to hold, enforce it on the server.

##### 💡 Implementation Tips:

-   **Reordering**: The buttons appear in the exact order you list them in the array
-   **Removing**: Simply omit any key (like `image`) from the array to disable that feature entirely for the user
-   **Native Fallback**: If you don't provide a `placeholder` in JS, the plugin will automatically use the `placeholder` attribute from your HTML `<textarea>`

### 🧩 Custom Tools

Add a toolbar button of your own without forking. Describe it and drop it into the `toolbar` array, in whatever position you want it.

<Snippet view="code">

```javascript
new MarkdownEditor('#markdown-editor', {
    toolbar: ['bold', 'italic', {
        custom: {
            title: 'Callout',

                editor.insertText('> [!NOTE]\n> Something worth noting');

```

</Snippet>

The `title` becomes the tooltip and the button's CSS class, so this one is styleable as `.callout-btn`, exactly like the built-in tools.

#### Several tools

Add as many as you like. Each one is its own entry in the array, so you place them individually and they can sit between built-in tools rather than being grouped at one end.

<Snippet view="code">

```javascript
toolbar: [
    'bold', 'italic',
    { custom: { title: 'Callout',   icon: svg1, action: insertCallout } },
    'ul', 'ol',
    { custom: { title: 'Signature', icon: svg2, action: insertSignature } },
    'preview'
```

</Snippet>

Give each one a distinct `title`. Two tools sharing a title would share a CSS class, and a tool without one falls back to `.custom-btn`.

#### Options

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Property | Type | Purpose |
| --- | --- | --- |
| `title` | `string` | Required. Tooltip text, and the source of the button's CSS class. Translatable through `locale`. |
| `action` | `function` | Required. Receives `(editor, event)`. The click event is passed on so a tool that opens a dialog can hand it to `MarkdownEditor.modal`. |

A tool with no `action` is skipped with a console warning rather than breaking the toolbar. It renders no button, and its `shortcut`, if it declared one, is not registered either.

#### Working with the content

Use `editor.insertText()` rather than writing to the textarea yourself. It replaces the selection, restores focus, moves the caret, scrolls, re-renders the preview and fires `onChange`. Undo keeps working because the edit goes through the normal path.

<Snippet view="code">

```javascript
action(editor) {
    const textarea = editor.usertextarea;
    const selected = textarea.value.slice(textarea.selectionStart, textarea.selectionEnd);
    const wrapped = `==${selected || 'highlight'}==`;

    // (text, where the caret lands, characters to leave outside the selection)
    editor.insertText(wrapped, wrapped.length, 0);
}
```

</Snippet>

#### A slow tool (async)

A tool that calls a server cannot finish inside the click. Put something in
the document straight away and swap it for the real text when the answer
arrives: a button that does nothing for two seconds reads as a broken button.
The image upload works exactly this way.

<Snippet view="code">

```javascript
async function rewrite(editor) {
    const textarea = editor.usertextarea;
    const selected = textarea.value.slice(textarea.selectionStart, textarea.selectionEnd);
    if (!selected.trim()) return;

    const token = `[${editor.label('Rewriting...')}]`;
    editor.insertText(token, token.length, 0);

    const put = (replacement) => {
        // Search for the token instead of remembering where it went. The
        // document keeps moving while the request is in flight, and it may
        // have been deleted altogether.
        const at = textarea.value.indexOf(token);
        if (at === -1) return;
        textarea.value = textarea.value.slice(0, at)
            + replacement + textarea.value.slice(at + token.length);
        textarea.setSelectionRange(at, at + replacement.length);
        editor.render();
        editor.notifyChange();
    };

    try {
        const response = await fetch('/api/rewrite', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ text: selected }),
        });
        if (!response.ok) throw new Error('HTTP ' + response.status);
        put((await response.json()).text);
    } catch (error) {
        put(selected);          // put their paragraph back
        console.error('[rewrite] failed', error);
    }
}
```

</Snippet>

Four things there are worth copying whatever your tool does:

-   **Insert a placeholder first.** `insertText` immediately, swap later.
-   **Find the placeholder by searching for it**, not by remembering an offset. The document moves while you wait.
-   **Restore the original if the call fails.** Losing someone's paragraph to a failed request is the one outcome worth engineering against. The image upload leaves a visible `Upload failed` marker for the same reason: a placeholder that silently disappears looks like nothing happened.
-   **Put the waiting text through `editor.label()`**, so it translates with the rest of the interface.

This is the shape for anything that waits: a translation service, a spell or
grammar check, a house-style linter, or a language model. The editor has no
AI of its own and no key of its own, so the endpoint is yours and the key
stays on your server, where a browser cannot read it.

#### Shortcuts

<Snippet view="code">

```javascript
{ custom: {
    title: 'Highlight',
    icon: '<svg>…</svg>',
    shortcut: 'Ctrl+Shift+H',
    action: (editor) => editor.insertText('====', 2, 2)
}}
```

</Snippet>

The tooltip becomes "Highlight (Ctrl+Shift+H)". Tool shortcuts are checked before the built-in ones, so a custom tool can deliberately take over a combination the editor would otherwise handle.

#### Tools that need their own markup

A dropdown or a dialog cannot be described declaratively, so write a class instead. Extend `MarkdownEditor.Tool`, set `this.button` in the constructor, and implement `applySyntax()`.

<Snippet view="code">

```javascript
class EmbedTool extends MarkdownEditor.Tool {
    constructor(editor) {
        super(editor, 'Embed video');        // tooltip, and .embed-video-btn
        this.shortcut = 'Ctrl+Shift+E';      // optional
        this.button = this.createButton('<svg>…</svg>');
    }

    applySyntax(event) {
        const dialog = MarkdownEditor.modal(event, 'fj:max-w-sm', `
            <input type="url" class="embed-url fj:me-input fj:w-full">
            <button type="button" class="embed-go fj:me-btn fj:me-btn-sm">Insert</button>
        `, 'Embed');

        dialog.querySelector('.embed-go').addEventListener('click', () => {
            const url = dialog.querySelector('.embed-url').value.trim();
            if (url) this.editor.insertText(`\n<iframe src="${url}"></iframe>\n`);
            dialog.close();
        });
    }

    destroy() {
        // Called by editor.destroy(). Release anything you registered here.
    }
}

new MarkdownEditor('#markdown-editor', { toolbar: ['bold', EmbedTool, 'preview'] });
```

</Snippet>

Pass configuration with `{ tool: EmbedTool, config: {...} }`, which arrives as the constructor's second argument. Setting `this.button` to `null` renders nothing, which is useful for a tool that only applies in some configurations.

One thing to watch: `Tool`'s constructor calls `createButton()`, so anything your override needs must come from `this.editor`, not from a field you assign after `super()`.

#### Two helpers your tool inherits

`Tool` gives you these, and a tool that wraps a selection wants both.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Helper | What it does |
| --- | --- |
| `this.trimSelection()` | Shrinks the selection so it holds no leading or trailing whitespace, then call your wrapping code. Double-clicking a word selects the space after it, so without this you get `**word **` and nothing renders as bold. Call it first in `applySyntax()`. Line-based tools should not: a trailing newline is what tells them which lines the selection covers. |
| `this.editor.label(text)` | Returns the translation for a string, or the string itself. Use it for anything your tool shows, so a `locale` can cover your tool as well as the built-in ones. |

</DocTable>

#### The dialog helper

`MarkdownEditor.modal` is the dialog the built-in link and image tools use, so a tool of yours that collects input looks like the rest of the editor instead of inventing its own popup. It returns the `<dialog>` element, already open, which you query for your fields and close with `dialog.close()`.

<Snippet view="code">

```javascript
// (event, size classes, body HTML, aria label)
const dialog = MarkdownEditor.modal(event, 'fj:max-w-sm', '…', 'Embed');
```

</Snippet>

Pass the `event` your `applySyntax()` received. The helper reads it to find which editor the click came from, so the dialog is appended inside that editor's wrapper and picks up its theme. It replaces any dialog already open in that editor, and removes itself from the DOM when closed, so there is nothing to clean up.

#### Rendering markdown yourself

If your tool embeds rendered content, a tooltip body for instance, `editor.renderMarkdown()` produces HTML exactly as the preview does, honouring your `renderer` and `sanitizer`.

<Snippet view="code">

```javascript
const html = editor.renderMarkdown('**bold** text');
```

</Snippet>

#### A toolbar for your own textarea

When a dialog collects rich text, give it the real formatting tools instead of rebuilding them. The toolbar is bound to the textarea you pass, your `locale` strings are inherited, and no preview button is added.

<Snippet view="code">

```javascript
const body = dialog.querySelector('textarea');
const bar = editor.createToolbar(body, ['bold', 'italic', 'strikethrough']);
dialog.querySelector('.body-toolbar').appendChild(bar);
```

</Snippet>

This does not manage the toolbar's lifetime. The buttons are cleaned up with the dialog when it is removed, but if a tool in it registers anything page-wide, a document listener or a timer, release that yourself when the dialog closes.

#### Translation

Custom tools translate like built-in ones, keyed by the title you gave them.

### 🌙 Theming

**MarkdownEditor** automatically inherits its theme from the surrounding page: no configuration required. The editor reads `data-theme` from the nearest ancestor at initialisation, so it stays in sync with your site's theme out of the box.

1.  **`theme` option**: explicit override passed in the options object
2.  **`data-theme` on the `<textarea>`**: set directly on the element
3.  **`data-theme` on any ancestor**: e.g. `<html>`, `<body>`, or a wrapper `<div>`

#### Available themes

`'light'` (default), `'dark'`, `'snowberry'`, `'darkberry'`

```html
  </script>
```

### 🌐 Interface Language

The editor's own text, tooltips, menu items, modal fields and buttons, is English by default. Pass a `locale` object to translate it. Keys are the English strings, the way gettext works, so you only list what you want to change and anything missing falls back to English.

`locale` takes the strings themselves, not a language code. `locale: 'es'` has no effect and says so in the console. Import the one you want instead, so nobody downloads the languages they are not using. It was called `labels` before 2.0.0, and that name still works.

<Snippet view="code">

```javascript
new MarkdownEditor('#markdown-editor', {
    locale: {
        'Bold': 'Gras',
        'Italic': 'Italique',
        'Heading': 'Titre',
        'Link': 'Lien',
        'Image link': 'Lien de l\'image',
        'URL': 'URL',
        'Alt text': 'Texte alternatif',
        'Apply': 'Appliquer',
        'Uploading...': 'Téléversement...',
    },
});
```

</Snippet>

This matters most alongside right-to-left content. Arabic, Urdu and Farsi lay out correctly on their own, but a toolbar that still reads "Bold" over right-to-left text is only half translated.

#### The full list of strings

There are 45 of them, and the package ships the list so you do not have to go looking. Keys and values are identical, so it is a template to copy rather than a translation.

<Snippet view="code">

```javascript
import template from 'markdown-text-editor/locale/template.js';
// { "Bold": "Bold", "Match case": "Match case", "{n} words": "{n} words", ... }
```

</Snippet>

Counts carry a `{n}` placeholder so your translation decides where the number goes, rather than being stuck with English word order.

<Snippet view="code">

```javascript
locale: {
    '{n} words': '{n} palabras',
    '{n} chars': '{n} caracteres',
}
```

</Snippet>

#### Using your own translations

`locale` takes a plain object, so where it comes from is up to you. Most projects already have a translation system, and feeding the editor from it keeps the wording consistent with the rest of the interface. In Django the strings end up in your `.po` files with everything else:

<Snippet view="code">

```python
from django.utils.translation import gettext as _

def edit(request):
    return render(request, 'edit.html', {
        'mte_strings': {
            'Bold': _('Bold'),
            'Italic': _('Italic'),
            'Apply': _('Apply'),
            'Uploading...': _('Uploading...'),
        },
    })
```

</Snippet>

<Snippet view="code">

```html
{{ mte_strings|json_script:"mte-strings" }}

<script type="module">
    const strings = JSON.parse(document.getElementById('mte-strings').textContent);
    new MarkdownEditor('#markdown-editor', { locale: strings });
</script>
```

</Snippet>

With a client-side catalogue such as i18next or vue-i18n, map the keys through your `t()`:

<Snippet view="code">

```javascript
import template from 'markdown-text-editor/locale/template.js';

const strings = Object.fromEntries(
    Object.keys(template).map(key => [key, i18n.t(`editor.${key}`)])
);
```

</Snippet>

### 📋 Pasting Formatted Text

Copy a few paragraphs from a web page, a wiki or a word processor, paste them
in, and the headings, links, lists and tables arrive as markdown. Before, the
clipboard's plain text was all that came through and the formatting had to be
put back by hand.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Pasted | Becomes |
| --- | --- |
| Headings | `#` to `######` |
| Bold, italic, strikethrough | `**`, `*`, `~~` |
| Links and images | `[text](url)`, `![alt](src)` |
| Lists, nested to any depth | `-` and `1.`, indented |
| Code, inline and block | backticks, with the language where the source says |
| Blockquotes, rules, tables | `>`, `---`, pipe tables |

</DocTable>

Markdown characters in the pasted prose are escaped, so a sentence containing
an asterisk stays a sentence rather than turning into emphasis.

The conversion declines more often than it acts. If the clipboard carries no
formatting worth converting, or the result would match the plain text anyway,
the browser does its own paste and keeps its own undo entry. A URL pasted over
a selection still becomes a link around that selection, which is the more
specific thing to have meant.

Pasted HTML goes through the same sanitizer as the preview, so a page carrying
a script tag or an inline event handler loses it on the way in.

<Snippet view="code">

```javascript
// Always paste plain text, as it worked before 2.0
new MarkdownEditor('#markdown-editor', { pasteHtml: false });
```

</Snippet>

### 💾 Draft Recovery

A tab crashes, a laptop sleeps and never wakes, somebody closes the wrong
window. Whatever was typed and not submitted is gone, because the only copy
of it was in a textarea.

`autosave` keeps a second copy in the browser and offers it back.

<Snippet view="code">

```javascript
new MarkdownEditor('#content', { autosave: true });
```

</Snippet>

Type, wait a second, and the draft is saved. Come back to a page whose text
no longer matches it and a strip appears above the toolbar:

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| | |
| --- | --- |
| **Unsaved draft**, with the time it was taken | `Restore` puts it in the editor, `Discard` throws it away |

</DocTable>

#### It never restores on its own

This is the part worth understanding, because it looks like a missing
feature until you have been bitten by the alternative.

The text your server put in the textarea may be **newer** than the draft:

```
Monday     you type a draft                     saved in your browser
Monday     you leave without submitting
Tuesday    a colleague edits the same document  the server is now newer
Wednesday  you open the page                    their text is in the box
```

An editor that restored automatically would put Monday's draft over Tuesday's
work and say nothing. Nothing on this side can tell which version is wanted,
so it asks, and the text on the page is untouched until you answer.

#### Looking before you choose

The strip has **one button**, **Review**. It opens a dialog holding the difference: the
lines the draft would take out, the lines it would put in, and a few either
side to say where in the document it happened, with the length of each version
above it.

By line rather than by character, since a character diff of two paragraphs is a
confetti of fragments and whole lines are what a reader answers from.

Both strips close. On the offer that means **not now**: the draft stays in
storage and is offered again on the next load, because unsaved work that
stopped asking after one dismissal would go quiet and then expire. Discarding
is the other thing, and it is behind the dialog where it can show what it is
about to delete.

Both answers leave the strip behind, saying what happened and offering
**Undo**, and it goes when you use it or when you next type. Closing that one
is not undoing: the answer stands.

Undo puts the draft back in storage either way, and after a restore it reverses
the document change as well. So neither accidental click destroys anything: the
strip comes back and you are where you were before it. Discard needs this more
than restore does -- restoring is one editor undo step regardless, while a
discarded draft has nothing else to give it back.

**Restore** and **Discard** are in the dialog and nowhere else. Both are
irreversible -- one overwrites the document, the other deletes the only copy of
the draft -- and neither is a thing to do from a bar that appeared while you
were reading something else. The strip costs nothing to ignore, which is the
quick path if the draft is not what you want.

Without it, pressing Restore was the only way to find out what a draft held,
which made looking and committing the same action. On a draft written against
text a colleague has since changed, that is the worst pairing available: the
warning tells you the choice costs something without telling you what, and the
only way to find out is to pay.

By line rather than by character: a character diff of two paragraphs is a
confetti of fragments, and the question being answered is "is this mine",
which whole lines answer.

#### Restore is one undo step

`Ctrl+Z` puts the page's text back. That matters most in the case above, where
a draft and the server disagree: Restore is reversible, so the worst that
happens is you look and change your mind.

Until 2.0 it was not. Assigning the textarea's value raises no input event, and
the undo history is built from those, so the replaced text had nowhere to go.
Restoring also clears the stored draft, which left reloading the page as the
only way back, and nothing said so.

#### When the page has moved on

The draft remembers the text the textarea held when it was taken. If the
textarea starts with something else today, somebody saved in between, and the
strip says so and turns amber:

```
unchanged   Unsaved draft   17/11/2026, 10:18
changed     Unsaved draft   17/11/2026, 10:18   The document has changed since then
```

Restoring is still offered, because the draft may well be the version you
want. You now know it costs you their edit. `Ctrl+Z` undoes a restore if you
change your mind.

#### Off unless you ask

Every other option here defaults on. This one does not: it writes what
somebody is typing to a disk this library does not own, on machines that are
sometimes shared, and that is a decision for the application rather than a
default.

#### Where the draft is kept

In `localStorage`, under a key built from the page address and the field's own
`id` or `name`:

```
mte:draft:/posts/7/edit:content
```

Two editors on a page are two drafts. The same form at two addresses is two
records, and the query string and hash count: `/edit?id=7` and `/edit?id=9`
do not share a draft, nor do `/#/posts/7` and `/#/posts/9`.

Where the address carries something incidental, a campaign parameter say, give
the key yourself. Your application knows what identifies the record:

<Snippet view="code">

```javascript
new MarkdownEditor('#content', {
    autosave: {
        key: 'post-7',        // instead of the address
        maxAge: 86400000,     // drop drafts older than a day; a week by default
        debounce: 1000,       // how long after typing stops, in milliseconds
    },
});
```

</Snippet>

If the textarea has no `id` or `name`, the key falls back to the field's
position on the page and the console says so. Positions move when a textarea
is added above, and two drafts change places with them.

#### What clears it

-   **Restore** and **Discard**, both, from the dialog.
-   **Submitting the form.** At that point the application has the text for real.
-   **Typing the document back** to what it started as. That is not unsaved work.
-   **Age.** Drafts older than `maxAge` are dropped unread.

#### Things to know

-   **Nothing leaves the browser.** The draft is never sent anywhere. It is not a backup, and it is gone when site data is cleared.
-   **It is not version history.** One draft per field, overwritten as you type.
-   **Storage can refuse.** Private browsing throws on access rather than returning null, and a full quota throws on write. Both are caught, so typing carries on either way, but a refused write is reported in the console rather than passed over: a draft that is not being kept is worth knowing about before you need it.
-   **There is a size limit, and it is the browser's.** `localStorage` holds roughly 5MB per origin, shared with everything else your application keeps there, and it counts UTF-16, so a million characters is about two of those megabytes. A document long enough to pass that cannot be drafted locally; the console says so when it happens.

### 🏷 Variables

Adds a toolbar dropdown for inserting placeholders. Useful when the person writing a document is not the developer who defined the placeholder syntax, as with email, invoice or contract templates: they pick a readable name and the correct syntax is inserted for them.

**Not on the default toolbar**, because the list of placeholders can only come from you. Put `'variables'` in `toolbar` for the button and the list in `variables`; given none, the tool adds no button at all.

<Snippet view="code">

```javascript
new MarkdownEditor('#markdown-editor', {
    toolbar: ['bold', 'italic', 'link', 'variables', 'preview'],
    variables: [
        { label: 'Customer Name', value: '{{customer.name}}' },
        { label: 'Invoice No',    value: '{{invoice.number}}' }
    ]
});
```

</Snippet>

`'variables'` sits wherever you put it in the array, so its position among the
other buttons is up to you. The button lists the labels, and clicking one
inserts its `value` at the cursor, replacing any selection. Nothing is rendered
if the list is empty.

The list is read whether or not the button is on the toolbar, because two other
things need it: the preview substitutes sample values, and the typed completion
below reads the punctuation your placeholders use. Both run before the toolbar
is built.

Before 2.0 the list was configured inside the toolbar array, as
`` `{ variables: [...] }` ``. That still works, so nothing written against 1.7
needs touching. Where both are given, the top-level option wins.

#### Sample values in the preview

An entry given a `sample` shows that sample in the preview, while the textarea keeps the real placeholder. Entries without one appear as written, so you can mix both.

<Snippet view="code">

```javascript
{ variables: [
    { label: 'Customer Name', value: '{{customer.name}}', sample: 'Hannes' },
    { label: 'Invoice No',    value: '{{invoice.number}}' }
]}

// textarea : Hi {{customer.name}}, invoice {{invoice.number}}
// preview  : Hi Hannes, invoice {{invoice.number}}
```

</Snippet>

#### Grouping

Give an entry `items` instead of a `value` to render a headed section. Grouped and flat entries can be mixed in one list.

<Snippet view="code">

```javascript
{ variables: [
    { label: 'Today', value: '{{today}}', sample: '10 September 2026' },
    { label: 'Customer', items: [
        { label: 'Name',  value: '{{customer.name}}',  sample: 'Hannes' },
        { label: 'Email', value: '{{customer.email}}', sample: 'hannes@example.com' }
    ]},
    { label: 'Invoice', items: [
        { label: 'Number', value: '{{invoice.number}}' }
    ]}
]}
```

</Snippet>

#### Completing as you type

Typing `{{` opens the same list under the cursor, narrowed as you keep typing
against both the label and the placeholder. The arrow keys move through it,
`Enter` or `Tab` inserts, and `Escape` closes it. Closing braces already after
the cursor are swallowed rather than left behind.

What opens it comes from your own placeholders, not from a fixed rule. The
editor reads the punctuation each `value` starts and ends with, so whatever
you write is what people type:

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Your `value` | Opens on | Inserts |
| --- | --- | --- |
| `{{today}}` | `{{` | `{{today}}` |
| `{{ today }}` | `{{` or `{{ ` | `{{ today }}` |
| `<< today >>` | `<<` | `<< today >>` |
| `[[today]]` | `[[` | `[[today]]` |
| `today` | nothing to type | toolbar button only |

</DocTable>

One optional space after the opening, because Handlebars and Mustache write
`{{today}}` while Django, Jinja and Liquid write `{{ today }}`, and someone
used to the second types the space out of habit.

A closing already sitting after the cursor is swallowed whatever its shape, so
an editor that auto-closes brackets does not leave you with `<< today >>>>`.

Mixing delimiters keeps them apart. With both `{{customer.name}}` and
`<< today >>` configured, typing `{{` offers only the first and `<<` only the
second, on the grounds that a host using both means them for different
things.

The dropdown stays, for the first time someone meets a template. The
completion is for every time after that, when the name is already known.

Nothing is inserted unless a key says so, so `{{` typed for its own sake
costs a dismissed menu. To turn it off, give `variables` its object form and
set `complete: false`:

<Snippet view="code">

```javascript
new MarkdownEditor('#markdown-editor', {
    toolbar: ['bold', 'italic', 'variables', 'preview'],
    variables: {
        items: [{ label: 'Customer Name', value: '{{customer.name}}' }],
        complete: false,
    },
});
```

</Snippet>

This was `variableComplete` at the top level in the 2.0 betas. It moved in with
the list it belongs to, and the old name says where it went in the console
rather than being ignored.

#### Things to know

-   **The editor never resolves variables.** It inserts text, and your application substitutes real values later, usually server-side. `sample` only affects what the preview displays.
-   **Labels are shown as plain text**, so markup in a label is never rendered.
-   **Malformed entries are skipped** rather than throwing, and the button is not rendered at all when nothing usable is configured.

### 🖋 Custom Renderer

The preview is rendered with [marked](https://marked.js.org) and sanitized with [DOMPurify](https://github.com/cure53/DOMPurify). Both can be replaced. Use this when your application already renders markdown with another library and you want the preview to match production exactly.

Both options are plain functions that take a string and return a string, so any parser and any sanitizer works.

<Snippet view="code">

```javascript
import MarkdownIt from 'markdown-it';
import taskLists from 'markdown-it-task-lists';
import MarkdownEditor from 'markdown-text-editor';

const md = new MarkdownIt({ linkify: true, breaks: true }).use(taskLists);

new MarkdownEditor('#markdown-editor', {
    renderer: markdown => md.render(markdown)
});
```

</Snippet>

DOMPurify still runs on the output, so you keep XSS protection without configuring anything.

#### Custom sanitizer

Only needed when the default strips something your renderer emits. DOMPurify removes `<iframe>` by default, so video embeds need it allowed explicitly. DOMPurify must be imported in your own code, since the copy bundled with the editor is internal.

<Snippet view="code">

```javascript
import DOMPurify from 'dompurify';

new MarkdownEditor('#markdown-editor', {
    renderer:  markdown => md.render(markdown),
    sanitizer: html => DOMPurify.sanitize(html, {
        ADD_TAGS: ['iframe'],
        ADD_ATTR: ['allow', 'allowfullscreen', 'frameborder']
    })
});
```

</Snippet>

Using a script tag instead of a bundler, load DOMPurify alongside the editor:

<Snippet view="code">

```html
<script src="https://cdn.jsdelivr.net/npm/dompurify"></script>
<script src="https://cdn.jsdelivr.net/npm/markdown-text-editor"></script>
```

</Snippet>

#### Things to know

-   **Preview only.** Hybrid mode's live formatting uses a separate internal renderer and is not affected.
-   **Task lists need plugin support.** Clickable checkboxes are found by looking for `input[type="checkbox"]` in the output, so markdown-it needs `markdown-it-task-lists`. The editor logs a warning if it detects task list syntax and no checkboxes.
-   **Both must be synchronous** and return a string. An `async` function writes `[object Promise]` into the preview.
-   **Replacing the sanitizer replaces your protection.** A pass-through such as `html => html` disables sanitizing entirely and is only safe for fully trusted content.

### 🪟 Fullscreen & Layering (z-index)

In fullscreen the editor uses `z-index: 10000`, which clears the layers most UI frameworks reserve for fixed headers and overlays. If a fixed header or sidebar still covers the editor, raise this value.

Override it with `--mte-fullscreen-z-index`. The value applies only in fullscreen, and it inherits, so setting it on any ancestor covers every editor beneath it.

```css
    --mte-fullscreen-z-index: 20000;
```

### 🔒 Content Security Policy

The editor adds no inline event handlers, uses no `eval`, and from 2.0.0 injects no `<style>` element. A strict policy needs no `'unsafe-inline'` exception for it, in either direction:

<Snippet view="code">

```
Content-Security-Policy: script-src 'self'; style-src 'self'
```

</Snippet>

Before 2.0.0 the CSS was carried inside the JavaScript and injected at load, which a policy without `style-src 'unsafe-inline'` refuses ([#42](https://github.com/nezanuha/markdown-text-editor/issues/42)). A nonce was considered and dropped: it only helps policies that have one, and a statically hosted site on `style-src 'self'` has no server minting a fresh nonce per request. Linking the stylesheet covers every policy instead of some of them.

One thing the editor does not control is the markdown your users write. DOMPurify keeps `style` attributes by default, so `<span style="color:red">` in a document survives into the preview and a strict `style-src-attr` will report it. Strip them with the `sanitizer` option if that matters to you:

<Snippet view="code">

```javascript
import DOMPurify from 'dompurify';

new MarkdownEditor('#markdown-editor', {
    sanitizer: html => DOMPurify.sanitize(html, { FORBID_ATTR: ['style'] }),
});
```

</Snippet>

## Content API

One of the core strengths of **MarkdownEditor** is that it keeps the underlying `<textarea>` perfectly synchronized. Whether you are using a modern JavaScript framework or a traditional backend like **Django, PHP, or Laravel**, the workflow remains simple and native.

### Reading and Writing Content

#### 1\. The Native Way (Recommended)

Because the editor enhances a standard textarea, you can use familiar DOM methods. This is the fastest way to interact with your data without learning a new API.

<Snippet view="code">

```javascript
// Retrieve content via ID
const markdown = document.getElementById('markdown-editor').value;

// Set content via ID (The editor UI updates automatically)
document.getElementById('markdown-editor').value = "# New Heading Content";
```

</Snippet>

#### 2\. Using a Variable Reference

If you have a reference to the textarea element, you can use it directly: no library-specific API needed.

<Snippet view="code">

```javascript
const textarea = document.getElementById('markdown-editor');

// Retrieve content
const markdown = textarea.value;

// Set content (the editor UI reflects this immediately)
textarea.value = "## Updated via JS";
```

</Snippet>

#### 3\. Setting initial content server-side

The recommended way to set initial content is directly in the `<textarea>` HTML: this works naturally with every backend framework (Django, Laravel, Rails, PHP, etc.) and the editor renders it automatically on init.

<Snippet view="code">

```html
<!-- Recommended: set content server-side -->
<textarea id="markdown-editor"># Hello World</textarea>
```

</Snippet>

To read or update content at runtime, use the native `textarea` value. Call `editor.render()` after an update to refresh the preview and hybrid layer.

<Snippet view="code">

```javascript
const textarea = document.getElementById('markdown-editor');

// Read
const markdown = textarea.value;

// Update at runtime
textarea.value = '# New content';
editor.render();
```

</Snippet>

#### 4\. Tearing down the editor: `destroy()`

Call `editor.destroy()` to remove the editor DOM wrapper and restore the original `<textarea>` to its position in the document. Useful in single-page applications when unmounting a view.

<Snippet view="code">

```javascript
const editor = new MarkdownEditor('#markdown-editor');

// Remove the editor and restore the plain textarea
editor.destroy();
```

</Snippet>

### Reacting to changes with `onChange`

Pass an `onChange` callback to be notified on every content change. Receives the current markdown string.

<Snippet view="code">

```javascript
const editor = new MarkdownEditor('#markdown-editor', {
    onChange(value) {
        console.log('Content changed:', value.length, 'characters');
    }
});
```

</Snippet>

#### Saving a draft

The editor does this itself from 2.0, so there is nothing to write:

<Snippet view="code">

```javascript
new MarkdownEditor('#markdown-editor', { autosave: true });
```

</Snippet>

Hand-rolling it with `onChange` and `localStorage` used to be the advice here,
and it is worth saying why that advice was wrong rather than merely longer. The
obvious version restores the saved text over whatever the page was loaded with:

<Snippet view="code">

```javascript
if (saved && !textarea.value) textarea.value = saved;   // don't
```

</Snippet>

The text already on the page came from your database and may be the newer of
the two, so overwriting it without asking can quietly lose an edit made
somewhere else. [Draft Recovery](#draft-recovery) offers the draft back with
the time it was taken and lets the writer choose, clears it when the form
submits, and drops drafts older than `maxAge` unread.

Use `onChange` for persistence the editor cannot do for you, such as saving to
your own server:

<Snippet view="code">

```javascript
let pending;
new MarkdownEditor('#markdown-editor', {
    onChange(value) {
        clearTimeout(pending);
        pending = setTimeout(() => {
            fetch('/api/posts/42/draft', { method: 'PUT', body: value });
        }, 2000);
    }
});
```

</Snippet>

### Form Submission

Because **MarkdownEditor** is built directly on the native `<textarea>`, it is compatible with every backend framework (Django, Laravel, PHP, Ruby on Rails, etc.) right out of the box.

This is where the "Native-First" philosophy shines. You don't need to manually sync data before submitting a form. The browser treats the editor exactly like a standard input field.

<Snippet view="code">

```html
<form method="POST" action="/api/submit">
  <textarea id="markdown-editor" name="content" class="h-48" rows="5">
    # Initial Content
  </textarea>

  <button type="submit">Submit to Server</button>
</form>

<script>
  // Just initialize it. That's it.
  new MarkdownEditor('#markdown-editor');
</script>
```

</Snippet>

<RawHtml html={"<p class=\"text-sm\"><strong>Note:</strong> MarkdownEditor plugin initialization mandatory</p>"} />

Just use a standard HTML `<form>`. The `name` attribute on the textarea is what your server will use to identify the content.

##### 🚀 Why it's a Game-Changer for Backends

Since the editor preserves the native `<textarea>` behavior, your server handles the data as a standard string. There is zero extra logic required: no `preventDefault()` and no manual `FormData` construction.

##### 💡 Why this is a "Killer Feature":

Most editors (like Quill, Editor.js, simpleMDE, easyMDE) save data in complex JSON structures. If a developer uses those, they have to rewrite their database schema and their rendering logic.

With **MarkdownEditor**, a developer can take an old website, replace a plain `<textarea>` with your editor, and the **backend doesn't even know it changed**. It just receives the same raw text it always did, but the user gets a 10x better experience.

<DocTable wrapper="overflow-x-auto w-full" table="table table-xs not-prose">

| Framework / Language | How to access the Markdown content |
| --- | --- |
| PHP | `$_POST['content']` |
| Django | `request.POST.get('content')` |
| Node.js (Express) | `req.body.content` |
| Laravel | `$request->input('content')` |
| Ruby on Rails | `params[:content]` |

</DocTable>

## 🖼️ Uploading Files

A file reaches the editor three ways: the image button's file picker, a pasted
screenshot, and a file dropped onto the textarea. `upload` is where all three
go.

<Snippet view="code">

```javascript
new MarkdownEditor('#editor', { upload: '/api/upload' });
```

</Snippet>

That is the whole configuration for the common case. Your endpoint receives the
file as `multipart/form-data` and answers with a URL.

Before 2.0 this lived inside the toolbar, as
`{ image: { fileInput: { uploadUrl } } }`. That form still works and is
documented at the end of this section, but it tied uploading to the image
button: leave the button off the toolbar and pasting a screenshot stopped
working too. An endpoint is not a button.

#### Three forms

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Written as | Use it when |
| --- | --- |
| `upload: '/api/upload'` | Your endpoint answers with a URL. Most hosts. |
| `upload: { url, ... }` | You need a CSRF header, a size limit, file types past images, or your endpoint answers in its own shape. |
| `upload: async (file, alt) => url` | You do the request: a presigned PUT to S3, an upload library, anything the options below cannot describe. |

</DocTable>

#### Options

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Property | Type | Default | Purpose |
| --- | --- | --- | --- |
| `url` | `string` | — | Where the file is POSTed. The only required option. |
| `field` | `string` | `'image_file'` | Name of the form field carrying the file. Change it when your endpoint already exists and reads something else, rather than writing a second endpoint to rename one key. |
| `headers` | `object` | — | Sent with the request. Where a CSRF token goes when the framework wants one in a header: `X-CSRFToken` for Django, `X-CSRF-TOKEN` for Laravel. `Content-Type` is ignored, because the browser writes it itself with the multipart boundary. |
| `params` | `object` | `{}` | Extra form fields sent alongside the file: a folder, a post id, or a CSRF token in the body. |
| `response` | `function` | reads the shapes below | Reads your endpoint's answer, for a shape the editor does not already understand. Return a URL string or an object with `path` or `url`, and optionally `alt`. Throw to report a failure. |
| `accept` | `string[]` | `['image/*']` | What may be uploaded, as `'png'`, `'image/png'` or `'image/*'`. This decides what the editor will even look at: a type outside the list is left alone on paste and drop. Widen it and other kinds of file become uploadable. |
| `maxSize` | `number` | no limit | Largest file accepted, in bytes. Unlike `accept`, going over it is reported rather than ignored, because the file was one you said you would take. |
| `insert` | `function` | see below | What is written into the document once the upload lands. Receives `(file, url, alt)` and returns markdown. |
| `onProgress` | `function` | — | Called as the bytes go out, with `(file, loaded, total)`, for a progress bar of your own. Only fires for the built-in `url` upload; a function passed as `upload` reports its own progress. |
| `paste` | `boolean` | `true` | `false` leaves pasted files alone. |
| `drop` | `boolean` | `true` | `false` refuses dropped files. The drop is still swallowed, because letting it through hands the file to the browser, which navigates away and takes the unsaved document with it. |

</DocTable>

The alt text always travels as `image_alt`, whatever `field` is set to. There is
no option for it: an endpoint that cannot read `image_file`, because it already
exists under another name, can still read a string called `image_alt`.

#### Paste and drop

Paste a screenshot or drag a file onto the editor and it goes to the same
endpoint as the toolbar button. A placeholder appears at once so the editor
never looks frozen, and it is replaced with the real path when the upload
lands. If it fails, the placeholder becomes a visible marker rather than
vanishing, which without devtools open would look like nothing had happened.

Several files at once go up one at a time, so they land in the order they
arrived.

With no `upload` configured, pasting a file does nothing and the console says
what to add. A dropped file is swallowed all the same: letting the event
through would hand the file to the browser, which navigates to it and loses
whatever was unsaved.

Uploading no longer needs the image button on the toolbar:

<Snippet view="code">

```javascript
new MarkdownEditor('#editor', {
    toolbar: ['bold', 'italic', 'link', 'preview'],   // no image tool
    upload: '/api/upload',
});
```

</Snippet>

What that gives up is the dialog: there is no way to insert an image by typing
a URL, and no alt text field, so `image_alt` always arrives empty.

#### What lands in the document

Markdown has syntax for exactly one of these. Video and audio are raw HTML
because there is nothing else to write, and anything else is a link named after
the file, which is what every forum and issue tracker does with an attachment.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Uploaded | Inserted |
| --- | --- |
| an image | `![alt](url)` |
| a video | `<video src="url" controls></video>` |
| audio | `<audio src="url" controls></audio>` |
| anything else | `[filename](url)` |

</DocTable>

Images are all that is accepted until you say otherwise. Widen `accept` and the
rest follows:

<Snippet view="code">

```javascript
new MarkdownEditor('#editor', {
    upload: {
        url: '/api/upload',
        accept: ['image/*', 'video/mp4', 'application/pdf'],
        maxSize: 50 * 1024 * 1024,
    },
});
```

</Snippet>

Writing the HTML for a video is a bet that whatever renders this markdown
allows HTML through. Most publishing pipelines do; `markdown-it` with
`html: false` and Python-Markdown do not, and there a reader sees the tag as
text. Give `insert` where that is true of yours:

<Snippet view="code">

```javascript
insert: (file, url, alt) => file.type.startsWith('video/')
    ? `[${file.name}](${url})`          // a link, because our renderer escapes HTML
    : `![${alt || ''}](${url})`,
```

</Snippet>

### 📡 Server Integration

#### The Request

A `POST` as `multipart/form-data`, carrying:

-   `image_file`: the file, or whatever `field` names
-   `image_alt`: the alt text the user typed, empty on paste and drop
-   anything in `params`
-   anything in `headers`, as headers

#### The Response

Answer with a URL. Any of these is understood without configuration:

<Snippet view="code">

```json
{ "url": "https://cdn.example.com/uploads/a.webp" }
{ "path": "/uploads/a.webp", "alt": "Two people looking at a laptop" }
{ "success": true, "image_path": "/uploads/a.webp", "image_alt": "optional" }
{ "success": false, "error": "The disk is full" }
```

</Snippet>

`url` and `path` are read first. `image_path` is the contract 1.8 shipped with
and still works, but an endpoint that stores PDFs should not have to call its
answer that.

`alt` or `image_alt` is a suggestion, used only where the user left the field
empty, so a server that derives alt text from the filename or from image
recognition can offer it without overwriting a real description.

**Answer `200` even when it failed.** The editor checks the HTTP status before
it reads the body, so a `422` or `400` is reported as a flat
`Upload failed: 422` and your `error` string is never seen. Keep non-2xx for
things the user cannot act on.

An endpoint that already exists in its own shape needs `response`, not a
rewrite:

<Snippet view="code">

```javascript
new MarkdownEditor('#editor', {
    upload: {
        url: '/api/media',
        field: 'file',
        response: body => body.data.public_url,
    },
});
```

</Snippet>

#### Django

<Snippet view="code">

```javascript
new MarkdownEditor('#editor', {
    upload: {
        url: '/api/upload/',
        headers: { 'X-CSRFToken': document.cookie.match(/csrftoken=([^;]+)/)?.[1] },
        maxSize: 5 * 1024 * 1024,
    },
});
```

<Snippet view="code">

```python
import uuid
from pathlib import Path

from django.contrib.auth.decorators import login_required
from django.core.files.storage import default_storage
from django.http import JsonResponse
from django.views.decorators.http import require_POST

ALLOWED   = {".jpg", ".jpeg", ".png", ".webp"}
MAX_BYTES = 5 * 1024 * 1024


def fail(message):
    # 200, not 4xx: the editor reads the status before the body
    return JsonResponse({"success": False, "error": message})


@login_required
@require_POST
def upload(request):
    file = request.FILES.get("image_file")
    if file is None:
        return fail("No file was sent.")

    suffix = Path(file.name).suffix.lower()
    if suffix not in ALLOWED:
        return fail("That file type is not allowed.")
    if file.size > MAX_BYTES:
        return fail("That file is over 5 MB.")

    saved = default_storage.save(f"uploads/{uuid.uuid4().hex}{suffix}", file)

    return JsonResponse({
        "url": default_storage.url(saved),
        "alt": request.POST.get("image_alt", ""),
    })
```

</Snippet>

```php
header('Content-Type: application/json');

$fail = fn($message) => die(json_encode(['success' => false, 'error' => $message]));

$file = $_FILES['image_file'] ?? null;
if (!$file || $file['error'] !== UPLOAD_ERR_OK) $fail('No file was sent.');
```

#### Validate on the server as well

`accept` and `maxSize` stop a 200 MB video leaving the browser, which is worth
having. They stop nothing else: your endpoint is reachable without this editor
in front of it. Every example above re-checks both.

The declared type is worth less than it looks, too. `$_FILES['type']` and
Django's `file.content_type` are both supplied by the browser and chosen by
whoever is uploading. The PHP example reads the magic bytes with `finfo`; do
the equivalent wherever it matters.

Large files also need the server told, or the request dies before your code
runs and the editor reports a flat `Upload failed: 413`:

<Snippet view="code">

```nginx
client_max_body_size 50M;
```

</Snippet>

#### Not through your server at all

Pass a function and the bytes never touch it:

<Snippet view="code">

```javascript
new MarkdownEditor('#editor', {
    upload: async (file, alt) => {
        const { uploadUrl, publicUrl } = await fetch(
            '/api/sign?name=' + encodeURIComponent(file.name)
        ).then(r => r.json());

        await fetch(uploadUrl, { method: 'PUT', body: file });
        return publicUrl;
    },
});
```

</Snippet>

Return a URL string, or an object with `path` or `url` and optionally `alt`.

<Snippet view="code">

```javascript
const bar = document.querySelector('#upload-progress');

new MarkdownEditor('#editor', {
    upload: {
        url: '/api/upload',
        accept: ['image/*', 'video/mp4'],
        maxSize: 50 * 1024 * 1024,
        onProgress: (file, loaded, total) => {
            bar.hidden = loaded === total;
            bar.value = loaded / total;
        },

```

</Snippet>

The image dialog's own button counts up on its own, with no configuration. An
endpoint that accepts video cannot leave a button saying nothing for a minute.

### The pre-2.0 form

`{ image: { fileInput: { uploadUrl, accept, params } } }` inside the toolbar
still works, so nothing written against 1.x needs touching. It says once per
page what replaced it, because the thing it cannot do is what people were
turning up to ask for.

<Snippet view="code">

```javascript
// still works, deprecated
toolbar: [{ image: { fileInput: { uploadUrl: '/api/upload' } } }]

// the same thing
upload: '/api/upload'
```

</Snippet>

`upload` wins where both are given. What moving it out buys: a CSRF token in a
header, your endpoint's own response shape, a size limit honoured on paste and
drop as well as in the dialog, file types past images, a progress callback, and
uploading with no image button at all.


### Image Alt Text Validation (`altInput`)

To ensure your content remains accessible and SEO-friendly, **MarkdownEditor** enforces alt text validation by default.

-   **Default Behavior**: If `altInput` is not defined, it defaults to `{ required: true }`
-   **Enforce Accessibility**: Users will be prevented from inserting an image until an alt description is provided

#### 1\. Default (No configuration needed)

<Snippet view="code">

```javascript
// Alt text is REQUIRED by default
toolbar: ['bold', 'image', 'preview'],
upload: '/api/upload'
```

</Snippet>

#### 2\. Shorthand (Disable Validation)

If you want to allow images without descriptions, simply set the boolean to `false`.

<Snippet view="code">

```javascript
image: {
  altInput: false // Users can now skip the alt text field
}
```

</Snippet>

#### 3\. Object-based (Explicit)

<Snippet view="code">

```javascript
image: {
    altInput: {
        required: false // Disables alt text validation — users can skip the alt field
    }
}
```

</Snippet>

### The image tool with no `upload`

With no endpoint configured the image dialog offers the URL field alone, which
is all you need if your users mostly link to images hosted elsewhere. Pasting
and dropping do nothing, and say so once in the console.

<Snippet view="code">

```javascript
const options = {
  toolbar: [
    'link',
    'image',
    'preview'
  ],
}
const editor = new MarkdownEditor('#markdown-editor', options);
```

</Snippet>

### 💡 CSRF tokens

Laravel and Django both refuse a file upload without one. Either place works:
`headers` puts it where the framework looks by default, as `X-CSRF-TOKEN` or
`X-CSRFToken`, and `params` puts it in the body as a form field, which is what
`_token` and `csrfmiddlewaretoken` are. The header is usually less work,
because the middleware already reads it and nothing has to reach the token at
render time.

## 🔍 Find & Replace

A find and replace panel built into the editor: no browser extension, no separate tool.

Open it with `Ctrl + F` (`⌘ F`), or with `Ctrl + H` (`⌘ H`) to open it with the replace row already showing. Every match in the document is highlighted at once with the one you are on picked out, and the counter reads as a fraction, `3/12`.

#### The switches

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Switch | Shortcut | What it does |
| --- | --- | --- |
| `Aa` | `Alt + C` | Match case |
| `ab` | `Alt + W` | Whole word only |
| `.*` | `Alt + R` | Read the search as a regular expression. `$1` and friends work in the replacement |
| `[ ]` | `Alt + L` | Search only the text you had selected. The range keeps covering the same text as you edit around it |
| `AB` | `Alt + P` | Keep the case of what you replace, so one lower-case replacement turns "Cat" into "Dog" and "CAT" into "DOG" |

</DocTable>

These work while the caret is back in the document as well as inside the panel, so you can click a match to read it in context and then change an option without going back to the box.

The panel is on by default. Set `find` to `false` to leave `Ctrl + F` to the browser's own find, for an editor whose documents are short enough not to need it.

<Snippet view="code">

```javascript
new MarkdownEditor('#editor', {
  find: false,
});
```

</Snippet>

#### Moving and replacing

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Key | Action |
| --- | --- |
| `Enter` / `Shift + Enter` | Next / previous match |
| `F3` / `Shift + F3` | The same, from anywhere in the document |
| `Ctrl + Alt + Enter` | Replace all |
| `Escape` | Close the panel and return to the text |

</DocTable>

#### Reading without a mouse or a screen

The panel is a labelled `search` landmark. Every switch reports its own pressed state rather than only looking different, each control carries its shortcut in `aria-keyshortcuts` as well as in its tooltip, and the arrows and replace buttons are disabled when there is nothing to act on instead of answering with silence. The match count is spoken once you stop typing rather than interrupting itself on every keystroke.

On a narrow editor the switches fold behind the chevron, decided by the panel's own width rather than the window's, so an editor in a narrow column behaves the same as one on a phone. Past four hundred matches only the current one is drawn, so a document full of a common word stays responsive.

## 📐 Editing Tables

With `table` on the toolbar, the button opens a grid to pick a size from rather than inserting a fixed template.

Click inside a table in the text and a small bar opens beside it:

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Control | What it does |
| --- | --- |
| Column `+` / `−` | Add a column after the one the cursor is in, or delete that column |
| Row `+` / `−` | Add a row below the one the cursor is in, or delete that row |
| Align left / centre / right | Set the alignment of the column the cursor is in |
| Tidy | Line the pipes up so the markdown source reads as a table |

</DocTable>

Keys work whether or not the bar is showing:

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Key | Action |
| --- | --- |
| `Tab` / `Shift + Tab` | Move to the next or previous cell |
| `Tab` in the last cell | Start a new row |
| `Enter` | Move down the column; from an empty row, leave the table |

</DocTable>

The bar comes with the `table` tool, so a toolbar without that tool has no bar.
Set `tableBar` to say otherwise: `false` turns it off for people who
would rather edit the pipes by hand, and `true` offers it on a toolbar with no
table button, which is what you want when the content already holds tables but
nobody should be inserting new ones. `Tab` between cells keeps working either way.

<Snippet view="code">

```javascript
// Table tool on the toolbar, but no bar
new MarkdownEditor('#editor', {
  toolbar: ['bold', 'italic', 'table', 'preview'],
  tableBar: false,
});

// No table tool, but tables already in the content can still be edited
new MarkdownEditor('#editor', {
  toolbar: ['bold', 'italic', 'preview'],
  tableBar: true,
});
```

</Snippet>

## 🧮 Maths

With `math` on the toolbar, the button or `Alt + M` wraps the selection in TeX delimiters: `$...$` on one line, `$$...$$` when the selection spans several. Pressing it again takes the delimiters off, whether they sit inside the selection or just outside it.

The editor writes the delimiters and nothing else. **It does not render TeX**, because maths is not part of markdown and a TeX engine is several times the size of the whole editor. What you get is portable markdown: GitHub, Obsidian and Jupyter all render it.

To see it rendered in the preview, pass a `renderer` that understands TeX, and load that renderer's stylesheet:

<Snippet view="code">

```javascript
import markdownIt from 'markdown-it';
import katex from '@vscode/markdown-it-katex';
import 'katex/dist/katex.min.css';

new MarkdownEditor('#editor', {
  toolbar: ['bold', 'italic', 'math', 'preview'],
  renderer: md => markdownIt().use(katex).render(md),
});
```

</Snippet>

Without one the preview shows `$x^2$` exactly as written, and the editor says so once in the browser console rather than leaving you to wonder whether the button worked.

## 🔗 Links from a pasted URL

Select some text, paste a URL over it, and you get a markdown link instead of the URL replacing what you selected.

<Snippet view="code">

```markdown
Read the docs                        <- select "the docs", paste https://example.com
Read [the docs](https://example.com) <- what you get
```

</Snippet>

The rule is deliberately strict: only a bare `http` or `https` URL with no whitespace is treated this way. Pasting a sentence that happens to contain a URL, or pasting with nothing selected, behaves like an ordinary paste.

## 🩺 What the console might tell you

The editor never fails silently at something you can fix. If it prints one of
these, this is what it means.

<DocTable wrapper="overflow-x-auto w-full not-prose" table="table table-md">

| Message starts with | What happened |
| --- | --- |
| *Stylesheet not loaded* | The CSS is a separate file in 2.x. Link `dist/markdown-text-editor.css`, or import `markdown-text-editor/style.css`. The editor works, it just looks unstyled. |
| *locale: '...' has no effect* | `locale` takes the strings, not a language code. Import the one you want from `markdown-text-editor/locale/`. |
| *toolbar takes an array of tools* | Something other than an array was passed, e.g. `toolbar: 'bold'`. The default toolbar is used instead. |
| *toolbar: no tool matches* | A name in the array is not a tool. Check the spelling against [Available Tools](#available-tools); the entry is skipped. |
| *A custom tool needs an action function* | A declarative `{ custom: {...} }` entry has no `action`. It renders no button. |
| *heading levels must be an array* | `{ heading: { levels } }` got something else. All six levels are offered. |
| *Maths syntax found, but nothing rendered it* | The editor writes `$...$` but does not render TeX. Pass a `renderer` that does, and load its stylesheet. |
| *Task list syntax found, but the custom renderer emitted no checkbox* | Your `renderer` does not handle `- [ ]`. The preview's checkboxes come from the renderer's output. |
| *The renderer threw* | Your renderer, or the default one, failed on this document. The preview falls back to plain text; what you typed is untouched. |
| *A file was pasted / dropped but no upload endpoint is configured* | Pass `upload` to accept pasted and dropped files. The drop is swallowed either way, so the unsaved document survives it. |
| *image.fileInput still works, but upload replaces it* | The pre-2.0 form, read once per page. Nothing is broken; `upload` is what lets paste and drop work without the image button. |
| *Image upload failed* | The endpoint answered with an error. The placeholder is marked in the text. |
| *tablePopover is now tableBar* | Renamed in 2.0. It only ever existed in a beta. |
| *variableComplete moved in with the list it belongs to* | It is `` `variables: { items, complete }` `` now. It only ever existed in a beta. |

</DocTable>

## Full Configuration Example

Everything in one place. Nothing here is required: `new MarkdownEditor('#editor')`
is a working editor, and most of what follows restates a default.

<Snippet view="code">

```javascript
import fr from 'markdown-text-editor/locale/fr';

const editor = new MarkdownEditor('#markdown-editor', {
    mode: 'hybrid',                 // 'plain' shows raw syntax. default plain
    placeholder: 'Start writing...',
    theme: 'light',                 // light | dark | snowberry | darkberry
    minHeight: 300,
    maxHeight: 700,

    toolbar: [
        'undo', 'redo',
        { heading: { levels: [2, 3, 4] } },
        'bold', 'italic', 'strikethrough', 'blockquote',
        'ul', 'ol', 'checklist', 'outdent', 'indent',
        'code', 'codeblock', 'math',
        'hr', 'table', 'link',
        { image: { altInput: { required: true } } },
        'variables',
        'preview'
    ],

    footer: { line: true, col: true, chars: true, words: true },

    find: true,                     // false leaves Ctrl+F to the browser
    tableBar: true,                 // omit to follow the toolbar
    pasteHtml: true,                // pasted rich text becomes markdown

    variables: [
        { label: 'Today',         value: '{{today}}', sample: '10 September 2026' },
        { label: 'Customer Name', value: '{{customer.name}}', sample: 'Hannes' }
    ],

    autosave: {                     // or just `true`
        key: 'post-42',
        maxAge: 7 * 24 * 60 * 60 * 1000,
        debounce: 1000,
    },

    upload: {
        url: '/api/upload',
        headers: { 'X-CSRFToken': csrf },
        accept: ['image/*', 'video/mp4'],
        maxSize: 50 * 1024 * 1024,
        onProgress: (file, loaded, total) => { bar.value = loaded / total; },
    },

    locale: fr,                     // or your own { English: translation }

    onChange(value) {
        console.log('Content updated:', value.length, 'characters');
    },
});

// Read content natively
const markdown = document.getElementById('markdown-editor').value;

// destroy() when the view unmounts (SPAs)
// editor.destroy();
```
